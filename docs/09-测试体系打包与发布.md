## 3. 任务清单

### S9-01 测试金字塔整理与目录规范

- **描述**：整理既有测试到五层目录：`tests/domain/`（纯领域单测）、`tests/application/`（fake 依赖的用例测试）、`tests/infrastructure/`（golden 与适配器测试）、`tests/integration/`（跨层 + 真实文件系统 tempdir）、`tests/e2e/`（可自动化的端到端）。统一命名与断言风格；引入 `cargo-nextest` 提速（可选，注意 Windows 兼容性）。
- **前置依赖**：阶段 03–07 的测试资产
- **涉及文件**：`tests/**`、`Cargo.toml`（`[[test]]` 声明）
- **验收标准**：`cargo test` 全绿且分层目录结构与上述一致；单测总耗时 < 60s（保证 Agent 迭代可接受）；flake 测试清零（连续 3 次运行结果一致）。

### S9-02 覆盖率门禁

- **描述**：配置覆盖率工具（`cargo-llvm-cov` 或 `cargo-tarpaulin`），设定门禁：整体 ≥ 70%、领域层 ≥ 90%；在 CI 中输出报告摘要并 fail 超标构建；明确排除项（derive 代码、错误 `Display` 实现、`#[cfg(test)]`）并写入 `docs/`。
- **前置依赖**：S3-14、S9-01
- **涉及文件**：`codecov.yml`（或等价配置）、`.github/workflows/ci.yml`、`docs/testing.md`
- **验收标准**：CI 覆盖率步骤红/绿可见；人为删除若干领域测试可验证门禁确实 fail；排除清单有书面理由，排除后领域层有效覆盖率仍 ≥ 90%。

### S9-03 属性测试补充（可选）

- **描述**：对文本缓冲与撤销栈这类「不变量丰富」的模块引入属性测试（如 `proptest`）：随机编辑序列后 `Rope` 与参考实现内容一致；随机 undo/redo 序列后内容回到某个合法历史状态；`byte_to_line_col` 与 `line_col_to_byte` 往返一致。**需评估体积与编译时间影响**，仅在 dev-dependencies 引入（不进 release 产物）。
- **前置依赖**：S5-01、S3-08
- **涉及文件**：`tests/infrastructure/rope_prop_test.rs`、`Cargo.toml`（dev-dependencies）
- **验收标准**：属性测试 ≥ 3 组，每组 ≥ 256 例；确认 dev-dependency 不影响 release 体积（`cargo bloat` 对比）；若体积/编译代价过大，降级为固定随机种子用例并记录理由。

### S9-04 三平台打包脚本

- **描述**：Windows：NSIS 或 portable zip（优先 zip 保证体积可控）；macOS：`.app` bundle + `.dmg`（`hdiutil`），需处理 `Info.plist`、图标、 hardened runtime；Linux：AppImage（+ 可选 `.deb`）。脚本需支持版本号注入、产物命名规范、校验和生成（SHA256）。
- **前置依赖**：S8-01、S8-07
- **涉及文件**：`scripts/package-windows.*`、`scripts/package-macos.sh`、`scripts/package-linux.sh`、`.github/workflows/release.yml`
- **验收标准**：三平台各产出一份可安装/可直接运行的产物；产物体积 ≤ 10 MB 且记录在发布说明；Windows 版在纯净虚拟机可启动、macOS 版通过 `codesign --verify`、Linux AppImage 在 Ubuntu 20.04 与 24.04 各启动一次；校验和文件随产物发布。

## 4. 技术方案要点

- **覆盖率是手段不是目的**：领域层 90% 是因为它是正确性核心；表现层不设高门槛（UI 逻辑靠阶段 07 的手工清单）。避免为凑覆盖率写无断言测试。
- **打包体积优先于安装体验**：Windows 首选 portable zip（无安装器开销），安装器作为后续版本增强；AppImage 体积大于裸二进制，需在预算内评估是否同时提供 tar.gz。
- **发布流程必须演练**：签名、notarize、Release 上传这类环节失败率高且难以本地复现，必须在预发布环境完整跑通一次再正式发布。
- **不引入遥测**：崩溃率目标通过「用户主动提交日志 + GitHub Issue」实现，避免为可观测性引入网络依赖与体积开销，也规避隐私合规问题。

## 5. 风险与注意事项

| 风险 | 等级 | 表现 | 应对 |
|---|---|---|---|
| macOS 公证（notarize）失败 | 中 | 用户首次打开被 Gatekeeper 拦截 | 未签名/未公证时 README 明确提示绕过方式；签名开启后 CI 增加 notarize 步骤并预演 |
| AppImage / deb 依赖差异 | 中 | 目标发行版缺依赖库 | Linux 优先静态链接（`wgpu` 依赖系统 Vulkan/GL，需实测）；提供依赖说明与最低版本 |
| 覆盖率门禁误伤 | 低 | 合法重构导致覆盖率小幅下降而红 | 阈值设 70/90 并留 2% 缓冲；重大重构时允许临时调整并记录 |
| 打包体积回升 | 中 | 打包环节引入额外资源（图标、运行时）超预算 | S8-07 的门禁覆盖打包后体积；资源压缩与图标尺寸控制 |
| 私钥泄露 | 高 | 证书/密钥误提交 | `.gitignore` 排除 + CI secrets + 发布前扫描；本地不存放明文私钥 |
| 文档与实现漂移 | 中 | README 声称的功能实际未实现（原型第 5 章的教训） | S9-07 的抽查验收；文档状态由阶段 07 的对齐矩阵驱动，不手写 |
