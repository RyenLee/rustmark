### OPT-001 · 体积归因从「单一总量」升级为「逐 crate `.text`」

| 要素 | 内容 |
|---|---|
| **手段** | 用 `cargo bloat --release --bin rustmark --crates 25` 做逐 crate 归因，并在 `docs/metrics.md` 区分「文件总大小」与「`.text` 段」两种口径 |

### OPT-003 · syntect 裁剪预案（20→10→5）：**评估后放弃执行**

| 要素 | 内容 |
|---|---|
| **手段** | 按 ADR-002 分级预案评估是否裁剪语言集 |

### OPT-007 · 空闲内存归因：**自有代码仅 ~0.9 MB，阈值与基线冲突**

| 要素 | 内容 |
|---|---|
| **手段** | 用「地板探针」（一个不引用本项目任何模块的空 eframe+wgpu 窗口，测完即删）与完整应用对比，把图形栈基线与自有代码分开 |
| **前值** | 只知道总数 189.2 MB（WorkingSet）/ 125.3 MB（Private WS），无法判断该优化哪里；§8.3 列的五项（Rope 唯一缓冲 / LayoutJob LRU 64 / Galley 缓存 / 纹理缓存 / 撤销栈上限）都是凭预估列的 |
| **后值** | 空窗口地板 124.4 MB（Private WS），完整应用 125.3 MB → **自有代码 + 全部依赖数据 ≈ 0.9 MB** |
| **代价** | 一次探针构建（45s）+ 两轮 12s 静置测量 |
| **结论** | ✅ **已裁定（需求方选「上调阈值」）** → **ADR-006**：`NFR-PERF-03` 改为「按平台各自阈值」，Windows 取 **≤ 150 MB**，判定口径由 WorkingSet64 改为 **Private Working Set**（实测 125.3 MB ✅ 达标，余量 19.7 MB）。原本的 ⚠️ 判定是：**这不是优化项，而是需求冲突**——≤100 MB 在 wgpu 后端下**连空窗口基线都过不了**（~125 MB），§8.3 五项即便全部做到极致，可省的也只是这 0.9 MB 的一部分。故 S8-04 结项为「**归因完成，不执行优化**」。被否决的另两个选项（维持 ≤100 MB 记未达标 / 换 glow 后端压基线）与否决理由见 ADR-006 |
| **待办** | macOS / Linux 阈值在 Stage 09 真机补测后填入 ADR-006 的阈值表；补测时**必须先做地板探针**分清图形栈基线与自有代码再定阈值，否则会重演本次「阈值与基线冲突」 |

### OPT-009 · 修复 DEF-03：release 二进制「启动即 panic」（wgpu 零后端）

| 要素 | 内容 |
|---|---|
| **手段** | 在 `Cargo.toml` 按平台补声明 wgpu 后端 feature：Windows `dx12` / macOS `metal` / Linux `vulkan+gles`（每个平台只启**一个**，避免开 `wgpu/default` 在各平台编译用不到的后端） |
| **前值** | release 二进制一启动就 panic：`No wgpu backend feature that is implemented for the target platform was enabled.` —— 对 eframe 关 `default-features` 后，`eframe/default → egui-wgpu/default → wgpu/default` 链断开，wgpu 只剩 `std`+`wgsl` |
| **后值** | 应用正常启动；冷启动 704 ms；`wgpu::Instance::enabled_backend_features()` 返回 `Backends(DX12)` |
| **代价** | 体积 **+0.414 MiB**（6.851 → 7.264 MiB，dx12 后端代码）；新增 `wgpu` 直接依赖声明（该 crate 本就在依赖树内，仅为打开 feature）；新增 `tests/startup_smoke.rs` 守卫断言 |
| **结论** | ✅ **必须修、已修**。这是发布级阻塞缺陷：一个能编译、能通过 1114 条测试、但**启动即 panic** 的二进制。教训：整个测试体系（单测 + 表现层 + headless `update`）都**不创建真实 wgpu 实例**，故该类配置缺陷有 0 覆盖 |

### OPT-010 · 高亮结果缓存：**空闲帧 56.5 ms → 0.01 ms（已做）**

| 要素 | 内容 |
|---|---|
| **手段** | `MarkdownAppService` 内新增 `HighlightCache`（键 = 文档 ID + 版本 + 语言 + 区间，容量 8），并在 `highlight()` 里对超过 `TRUNCATE_THRESHOLD_BYTES` 的源**直接返回空片段** |
| **前值** | 编辑区**每帧**无条件调用 `highlight()` 请求全文 span。文档未变的帧（滚动 / 空闲 / 切换面板）也照样付 syntect 全文解析的钱：10KB 一次 56.5 ms。1MB 文档更糟——每帧都要解析 1MB（秒级），而 mapper 在同等阈值上已降级为纯文本，这份 span **根本没人用** |
| **后值** | 空闲帧 **p50 0.01 ms / p95 0.02 ms**；超阈值文档不再进入高亮器（`call_count == 0`） |
| **代价** | 约 90 行缓存代码；每个文档多驻留一份 span（容量上限 8 个文档，超阈值文档不缓存） |
| **结论** | ✅ **已做**。键里带版本号 → 内容一改即失效，**语义与重算完全一致**，不存在「颜色滞后」。这是纯消除重复计算，没有任何行为变化 |

> 副产品：这次测量暴露了 `mapper` 对「span 与文本不同源」的情形不设防——
> 字节区间落到非字符边界时 `&line[lo..hi]` 会 panic，而本项目是 `panic="abort"`，
> 等于直接崩溃。生产路径（每帧重新高亮）天然同源，故未触发；
> 缓存键带版本号后更不可能触发。已记为 DEF-04，**已在 OPT-014 加固**。

### OPT-011 · 编辑帧 67.9 ms（syntect 全文重解析）：**已做（① 高亮防抖）**

| 要素 | 内容 |
|---|---|
| **手段** | ① **高亮防抖（已实现）**：`MarkdownAppService::highlight` 在文档版本刚变化后的 150 ms「静止窗口」内返回空片段（打字期不上色），`clock` 推进过窗口后再做 syntect 全文高亮一次。同时给 `mapper` 整文档缓存键加 `colored` 维度，避免防抖期排的纯文本 Galley 在停手后被命中而「颜色回不来」。② **增量高亮**（按行缓存 `ParseState`，只重解析变更行及其后直到状态收敛，需给领域 `SyntaxHighlighter` trait 加逐行接口）③ 接受现状并下调 `NFR-PERF-04` 适用场景——后两者均未采用 |
| **前值 / 后值** | 前值：编辑帧 p50 **67.9 ms**（10KB，超 16 ms 帧预算 4.2 倍）。后值：**打字期帧 ≈ 0.00 ms**（防抖期短路，不进 syntect）；停手后一次性全量高亮 **~59 ms**（每 150 ms 至多一次）。10KB 解析 p50 0.11 ms 不变 |
| **代价** | ① 的代价是「连续打字时语法色暂时消失」（FR-03 的观感降级），改动面在 application + presentation，未碰领域接口、未加依赖；② 未被选，因其代价是扩领域 trait + per-document 状态，属架构调整 |
| **结论** | ✅ **已做（选 ①）**。理由：② 触及领域接口、③ 放弃帧预算，两者都需重新裁定；① 在既有架构内闭环、观感降级可接受（停手即恢复）。实测见 `docs/metrics.md` §3.2 |

> **补充归因（同一轮追加，用于收窄候选）**：新增
> `measure_markdown_highlight_parse_vs_classify`，把一次 10KB 全量高亮拆成两段，
> 实测 syntect 逐行解析 **58.38 ms（97.4%）**、scope 判定与片段组装 **≈1.56 ms（2.6%）**
> （`docs/metrics.md` §3.2.1）。**这否决了第四条候选**：「给 scope → 样式加备忘表」
> 看似最省事、不改可见行为也不碰领域接口，但即便把它做到零成本也只省 2.6%，
> 编辑帧仍停在 58 ms 量级。故唯一能压住编辑帧的是「少解析」——而少解析只有
> ①（跳过）或 ②（增量）两条路，最终选 ①。

### OPT-012 · 预览防抖语义修复（节流 → 防抖）：**连续输入 20 字符重解析 7 次 → 2 次（已修）**

| 要素 | 内容 |
|---|---|
| **手段** | `PreviewUiState::mark_edited(now)` 新增打戳方法，在 `EditorApp::refresh_text()`（所有文本变更的共同路径）里调用 |
| **前值** | `last_edit_at_ms` 只在 `record_render()`（**渲染完成时**）更新 → 计时起点被每次渲染刷新，于是「距上次编辑 150 ms」实际变成「距上次渲染 150 ms」，语义从**防抖**退化成**节流**。实测连续输入 20 字符（60 ms/字符，共 1.2 s）重解析 **7 次**，验收上限是 2 次 |
| **后值** | 同样输入节奏下：输入期间 **1 次**、停手后补 **1 次**，累计 **2 次** ✅ |
| **代价** | 约 15 行；打戳点选在 `refresh_text()` 而非各编辑入口——编辑入口有十几处（输入 / 插入 / 替换 / 整篇变换 / 查找替换 / 领域命令…），漏一处就会重新退化成节流 |
| **结论** | ✅ **已修**。这是纯接线缺陷（「没人打时间戳」），不是策略错误：单独测 `should_render` 的纯函数永远测不出来，必须用 headless 驱动真实帧循环数 `render_count` 才能暴露 |

### OPT-013 · CI 门禁：体积红线与性能冒烟（已做）

| 要素 | 内容 |
|---|---|
| **手段** | ① 体积门禁由「只打印」升级为「超红线即 fail」（红线 10 MB / 预警 8 MB，`workflow_dispatch` 可覆盖阈值以便人为验证）；② 新增 `perf` job（仅 Linux 必过，release + `--test-threads=1` 跑 `measure_*`，其自带阈值断言即门禁）；③ `cargo bloat --crates 15` 写入构建摘要（`continue-on-error`） |
| **前值** | 体积只写进摘要、**超了也不红**（形同没有门禁）；性能基准只在本地偶尔跑一次 |
| **后值** | 超 10 MB 直接 `exit 1`；性能回归（10KB 解析 / 编辑区高亮帧 / 1MB 降级帧）会在 PR 上红；PR 摘要可见三平台体积与逐 crate 归因 |
| **代价** | `perf` job 要多跑一次 release 构建（约 1–2 min）；`cargo bloat` 需在 CI 现装（故设为可失败，仅诊断） |
| **结论** | ✅ **已做**。验收要求「人为调低阈值可验证 fail」已在本机验证：同一产物 7,620,608 B，阈值 10 MB 判 PASS、调低到 1 MB 判 FAIL。性能门禁只挂 Linux——跨平台绝对数字不可比，挂全平台会引入随机红（需求 §8 风险表已预见此点） |

### OPT-014 · 修复 DEF-04：表现层切片未防「span 与文本不同源」（已修）

| 要素 | 内容 |
|---|---|
| **手段** | 在 `shared::geometry` 增加两个字符边界原语：`floor_char_boundary`（越界裁剪 + 向下吸附）与 `clamp_to_char_boundaries`（返回可直接切片的安全区间，空区间给 `None`）；`presentation::theme::mapper::build_line_job` 把 span 与查找命中的**全部**边界过一遍吸附；`preview_view::draw_highlighted_code` 同样处理，并抽出纯函数 `highlighted_code_job` 以便无头断言 |
| **前值** | 两处都只把边界裁剪到 `line.len()` / `text.len()`，**未做字符边界检查**。`&line[lo..hi]` 一旦落在多字节字符中间即 panic，而本项目 `panic = "abort"` —— **一次就等于窗口消失，没有任何回退余地**。生产路径每帧重新高亮、span 与文本天然同源，故从未触发；但「同源」只是约定不是保证：缓存版本错位、手写区间、未来任何「复用上一版 span」的改动都能打破它 |
| **后值** | 任何外部坐标都先吸附到字符边界再切片：最坏只是**某一段少上色**，绝不崩。已用变异测试验证用例有效——把吸附改回旧逻辑后，3 条新用例全部以 `end byte index 1 is not a char boundary; it is inside '列'` 失败 |
| **代价** | 约 60 行（含 9 条单测）；正常路径多几次 `is_char_boundary` 判定（每行十几次，ns 量级）；`src/app/frame.rs` 里原本私有的同名 `floor_char_boundary` 已收敛到 `shared`，消除重复实现 |
| **结论** | ✅ **必须修、已修**。与 DEF-03 同类：**能编译、能过 1100+ 条测试、但真机会崩**。区别在于 DEF-03 是「一启动就崩」，DEF-04 是「特定时序下崩」——后者更值得在单测层钉死，因为它不会在 CI 里稳定复现 |

## 放弃的优化项（汇总）

| 项 | 放弃原因 |
|---|---|
| syntect 语言集裁剪（20→10→5） | 实测 < 37.8 KiB，距预算 40 倍余量；裁剪只会损失语言覆盖（OPT-003） |
| `opt-level="s"` 折中 | release 构建仅 1m30s，无需用体积换编译速度（OPT-005） |
| 引入 `criterion` 做基准 | 阶段 08 文档标注为「可选，注意体积与编译时间成本」；现有 `measure_*` 测试已能在 release 下给出 p50/p95，不值得为此增加依赖与编译成本 |
| §8.3 内存五项（Rope 唯一缓冲 / LayoutJob LRU 64 / Galley 缓存 / 纹理缓存 / 撤销栈上限） | 归因显示自有代码总内存仅 ~0.9 MB（OPT-007），五项即便全做完也没有可观测收益。改为**记录结论而非执行**；若需求方把阈值上调到可达区间后仍有缺口，再回来做 |
| 冷启动优化（语法预热等） | 682 ms 全在 eframe/wgpu 初始化，自有代码仅 3.0 ms（OPT-008）；语法预热（30 ms/语言）解决的是「首次滚到代码块的卡顿」，与冷启动无关，且其收益需真机交互验证 |
| 「scope 栈 → 样式」备忘表 | 归因显示判定与组装只占 **2.6%**（1.56 ms / 59.94 ms），97.4% 全在 syntect 解析（§3.2.1）；即便把判定做到零成本，编辑帧仍停在 58 ms 量级。此路不通，OPT-011 的三个原候选维持不变 |
