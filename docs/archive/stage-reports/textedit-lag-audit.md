> 写作日期：2026-10-16 ｜ 关联问题：046 ｜ 关联前置：044（egui 0.37 升级）、043（多文档卡顿）
> 性质：**一次性审计报告**（结论已被现行文档吸收：数字进 `docs/metrics.md` §3.2.2、
> 规则进 `src/shared/text.rs`）。归档后其中的「当前 / 待办」表述只在本写作日期成立。
>
> **为什么要写这篇**：`T.txt` 是一份针对 **egui 0.33** 的通用建议。
> 本项目在写这份审计之前刚完成 0.33.3 → 0.37.0 升级（问题 044），

> 「剩下那部分根本不是我们能修的」。

---

## 0. 一句话结论

`T.txt` 指出的三类成因在本项目**两类不成立、一类已被更细的实现覆盖**；
它给的三条方案里 **② 已满足、① 不可用、③ 已被 0.37 换掉 API**。
本项目真正剩下的每帧浪费与 `T.txt` 描述的不是同一件事——
是**我们自己**在帧路径上为两个整数付了 O(全文)，已修（问题 046，见 §4）。
修完后 1MB 文档的空闲帧仍有约 3.16ms 属 egui 自身的逐行开销，
那才是 `T.txt` 方案一的射程，而它在本期不可用。

---

## 1. 对「🎯 核心卡顿原因」三条的核实

### 1.1 成因①「每次编辑重新布局整个文本，耗时与文本总长度线性相关」

**部分成立，但本项目已把它切成逐行**。

`TextEdit` 每帧确实会调用我们传入的 layouter，但 layouter 的实现
（`presentation/theme/mapper/highlight_layout.rs::highlight_layout_with_find`）
不是「整篇重排」：

1. 先查**整文档缓存**（文本 / 主题 / 换行宽 / 查找命中 / 着色状态 / 排版度量 / 图集令牌
   全部一致即直接返回上一帧的 `Galley`）；
2. 未命中才逐行比对上一版行布局，用「前后缀 + 中段逐行配对」求出差分映射，
   **只重排真的变了的行**，其余行 `Arc` 复用，最后 `Galley::concat` 拼回。

实测（`docs/metrics.md` §3.2）：10KB 文档改一行只重建 **1** 行，增量帧 p50 远低于目标。
这比 `T.txt` 方案二的「段落级缓存」粒度**更细**（按行而非按段）。

### 1.2 成因②「Galley 缓存键基于整个 `LayoutJob` 哈希 → 每次编辑全失效」

**在 0.37 已经不成立，且本项目本来就不依赖它**。

- 本项目编辑区的排版**不经过** `Fonts::layout_job` 的整篇缓存，
  而是自己的两层缓存（整文档 + 逐行），见 1.1；
- 0.37 另外在 `epaint` 内部加了段落级缓存（PR #5411）：
  `GalleyCache::layout_internal` 在 `allow_split_paragraphs && break_on_newline &&
  wrap.max_rows == usize::MAX && text.contains('\n')` 时按 `\n` 切段逐段缓存，
  且 `FontsImpl::layout_job` 硬编码 `allow_split_paragraphs = true` →
  凡走 `layout_job` 的路径（预览区等）**已自动获益**，无需改动。

### 1.3 成因③「wgpu 后端字形分配退化 / 每帧变化的字号让字形永不可缓存」

**本项目两条都不同时成立**。

- 后端：`T.txt` 引用的是 0.33→0.34 过渡期的 wgpu 退化报告；本项目已到
  `wgpu 30.0.1` + `egui-wgpu 0.37`，且 wgpu 是需求 §5.1 的硬约束（ADR-001），
  不为性能改用 glow（glow 还会破坏体积预算的口径）。
- **字号不是每帧动态计算的**（这条是「字形缓存病态用例」的判定条件）：
  编辑区字号来自持久化设置 `theme.editor_font_size`
  （`presentation/theme/builtin.rs`），`mapper` 把 `TextStyle::Monospace` 映射到它，
  项目内**没有 zoom / 缩放**。故哈希键中的字号逐帧稳定，缓存不会被「永不命中」。
  `editor_metrics_signature(theme)` 把字号 / 行高并入了两层缓存的键——
  这正是「字号一变就整篇失效」这条假设的**显式防线**：不会读到错尺寸的旧 `Galley`。

### 1.4 结论：`T.txt` 的「成因」清单对本项目的解释力有限

它描述的是一份**通用**分析；本项目的编辑区早在 S6-04 起就自己做了逐行增量排版，
成因①②在这里基本不成立。真正被它对准的只有成因③的后半句（固定字号），
而我们已经满足。

## 2. 对「🛠️ 分场景优化方案」三条的核实

| 方案 | 本项目现状 | 判定 |
|---|---|---|
| **① 视口虚拟化**（`ScrollArea::show_viewport` + 文本切片） | 0.37 的 `TextEdit` **没有** `show_viewport` / `visible_range` / 部分排版能力（无该 API）。编辑区是 `TextEdit`（为拿到 IME、选词、撤销语义，S6-03 的既定取舍），**不可虚拟化**。 | **不可用**（改成自绘编辑器是架构级改动，不在本期范围） |
| **② 段落级缓存**（PR #5411，2000 行 ~8ms → ~300µs） | 已满足，且本项目在编辑区用的是**行级**缓存（更细）；0.37 的段落级缓存亦已内置并覆盖走 `layout_job` 的其它路径。 | **已满足，零改动** |
| **③ 渲染后端与字体优化** | 后端：见 1.3，不改。字体：字号固定 ✔（见 1.3）；`font_hinting` / `subpixel_binning` 在 0.37 从「`FontDefinitions` / `TextStyle` 上的开关」变成了 **`epaint::TextOptions`**（挂在 `egui::Visuals::text_options` 上，默认 `font_hinting = true` / `subpixel_binning = true`）。 | **可实施但与本案无关**（见下） |

### 2.1 为什么**没有**去关 `font_hinting` / `subpixel_binning`

- 这两个开关的代价落在**字形**上（`epaint::text::glyph_atlas` 的栅格化与图集占位），
  而本项目的实测归因（§4）显示每帧成本在**文本快照、行扫描、片段克隆**与
  **egui 的逐行 Galley 处理**上，不在字形分配。关掉它们不会改善 §4 里那几项。
- 二者都影响**观感**（`font_hinting` 关掉字变糊；`subpixel_binning` 关掉字距
  均匀度变差）。在拿不出「关掉之后本项目的空闲帧明显下降」的实测数字之前，
  为一个用户可见的清晰度代价去换一个未经验证的收益，不符合本项目的取舍纪律
  （可对比问题 019/022 里「视觉保真优先于体积/性能」的既有裁决）。
- `TextOptions` 现已可经 `ui.style_mut().visuals.text_options` 就地调整，
  将来若真有字形侧的证据，改动点是明确的、一行的事。

## 4. 本项目真正的问题（`T.txt` 未覆盖）与修复

审计顺带做了一次实测，发现每帧真正的浪费**不在排版、不在字形**，而是：

> **为两个整数付 O(全文)。**

`MarkdownAppService::highlight` / `spell_check` 每帧先 `fetch` →
`content_and_revision` → `Document::text()`，把整篇文本从 rope 快照成一个新 `String`；
而这一帧真正需要的只有**版本号**（防抖计时、缓存键）与**字节长度**（>500KB 降级）。
三者都是 O(1) 能拿到的（`DocumentRegistry::revision_of` / `Document::len_bytes`）。

同类问题还有三处：高亮结果按值返回导致每帧克隆整张片段表；
行数与光标行号用 `split('\n')` / `chars()` 而非字节扫描；
光标行号在**行号栏关闭时（默认）**也照算。

**修复见问题 046**，实测（release，100KB）：空闲帧 p50 0.56 → **0.33ms**，
高亮查询命中 0.108 → **0.000ms**，光标行号 0.102 → **0.027ms**；
1MB 空闲帧 4.44 → **3.16ms**，p95 8.33 → **4.06ms**。
完整归因表在 `docs/metrics.md` §3.2.2。

**修完剩下的 1MB ≈ 3.16ms 全部来自 egui** 对 58,514 行 `Galley` 的逐行处理
（该档已降级为纯文本、不着色，故不含 syntect）。这部分只有方案一能治，
而方案一在本期不可用（§2）。**结论：编辑区性能已到本项目可控边界。**

## 5. 可复用的一条判据（写给后续)

判断「某处该不该做逐帧优化」时，先问一句：

> **这份数据，本帧真的需要它「全部内容」吗？还是只需要它的元数据？**

本项目的三次同源教训分别是：
- 问题 043：预览区每帧为拿一个 `u64` 版本号克隆整篇文本；
- 问题 046：编辑区每帧为拿「版本号 + 长度」快照整篇文本、为「片段数量不变」克隆整张表；
- 全仓：四处各写一份 `split('\n').count()`（现收敛到 `shared::text::line_count`）。

配套的确定性回归手法：**用计数 fake 钉住「快照次数」**，
而不是用耗时阈值——亚毫秒级样本的抖动比信号还大，阈值只会带来 flaky。
