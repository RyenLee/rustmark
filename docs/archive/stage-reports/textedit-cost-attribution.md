## 0 一句话结论

1MB 击键帧 p50 **40.92ms**、超 `NFR-PERF-04`（16ms）2.6 倍，**瓶颈不在 egui、也不在排版层，
而在「文本变更」之后应用层那条链路**——它独占 **23.67ms（58%）**。

此前那条判定链「egui 无视口虚拟化 → 这笔钱花在框架里、本项目无法规避 → 要达标只能自绘编辑器」
**不成立**：自绘替换的是编辑表面与排版，而动不到这 23.67ms；更关键的是，本项目的自研排版层
在同样的裸宿主下**比上游默认排版还快 1.80ms**（§4.2）。

## 1 争议的由来：三处自相矛盾的表述

同一个文档集里同时存在三种说法，必须用测量裁决：

| 出处 | 说法 |
|---|---|
| `docs/spec/metrics.md` §3.2.3 结论 3 | 「文本一变就要重建 58,514 行的 `Galley`，42.00ms 与空闲帧 3.25ms 的差（约 39ms）来自这里」 |
| `docs/spec/metrics.md` §3.2.3 结论 1 | 「击键帧 = 空闲帧 + 增量重排……与 §3.2.2 的增量设计（**重建行数 == 1**）一致」 |
| `src/presentation/theme/mapper/highlight_layout.rs:110` | 「大文件降级：跳过 span 着色，**仍逐行缓存**」 |

结论 1 与结论 3 互斥。若结论 1 为真，则「重建 58k 行」的说法连同它推出的「只能自绘」都是错的。

## 2 实验设计

八组测量，同一语料（1MB 中文 Markdown，58,514 行，> 500KB 故走降级纯文本路径）、
同样注入**真实的** `egui::Event::Text`（而非直接改文本模型）、每帧显式推进 8ms（约 125fps 的连续人手节奏）。

| 组 | 被测对象 | 回答的问题 |
|---|---|---|
| E1 | 真实 `EditorApp`（当前实现，含逐行 layouter） | 指标口径下每帧到底几毫秒 |
| E2 | 直接调 `mapper::highlight_layout_with_find`（文本变一字节） | 「拆行 + 差分 + 重排 1 行 + concat」自己花了多少 |
| E2b | 同上但文本不变（整文档缓存命中） | 一次调用的底价（把簿记成本与调用开销分开） |
| E3 | 裸 `TextEdit` + **egui 默认 layouter** | 交给上游（含 0.37 的按段落缓存）要多少 |
| E7 | 裸 `TextEdit` + **我们的 layouter** | 同样的宿主、同样的文本，只换 layouter 净增多少 |
| E8 | 直接调 `editor_ops::diff_replace` | 应用层文本变更链里最大的一块嫌疑占多少 |

**公平性**：E3 与 E7 共用同一个探针函数（`bare_frame`），**唯一**差别是是否挂自定义 layouter；
两者都用 `ScrollArea::vertical` + 撑满视口的 `TextEdit`，与真实编辑区同构。
E7 − E3 因此干净地隔离出「自家逐行排版相对上游按段落排版的净开销」。
E1 − E7 则隔离出「`EditorApp` 的每帧前置工作 + 文本变更回写链」——裸宿主里没有这些。

**E3 为什么是「交给上游」的忠实对照**：裸 `TextEdit` 的默认 layouter 走 `LayoutJob::simple`，
其 `break_on_newline = true`、`wrap.max_rows = usize::MAX`（默认值，见
`epaint-0.37.0/src/text/text_layout_types.rs` 的 `simple` 与 `TextWrapping::default`），
且文本含 `\n`——恰好满足 epaint 0.37 `galley_cache::should_cache_each_paragraph_individually`
的三个条件，故上游会**按段落分别缓存、只重排改动段**（`layout_each_paragraph_individually`）。
反观本项目：`highlight_layout` 自己把整篇拆成**单行 job**，单行不含 `\n`，该条件恒为 `false`
——**上游这份按段落缓存从未生效过**，等价效果由我们自己的 `LINE_LAYOUT` 逐行 LRU 提供。

**计数优先**：「每帧究竟重建了几行」由 `mapper::last_highlight_stats().reshaped_lines` 给出，
与耗时无关、不受机器快慢影响。这是本报告最硬的一条证据。

## 3 实测数据（release，p50，单位 ms）

### 3.1 主表

| 量 | 数值 |
|---|---|
| **E1 现状击键帧** | **40.92**（p95 43.42） |
| E1 同运行空闲帧 | 7.06 |
| E1 每帧重建行数（100 帧） | **max = 1** |
| E2 排版层·文本变一字节 | 9.24（p95 11.17；重建行数恒 1） |
| **E2b 排版层·整文档缓存命中** | **0.238** |
| E3 裸 `TextEdit` + 上游默认 layouter | 19.04（p95 20.40） |
| E7 裸 `TextEdit` + 本项目逐行 layouter | 17.24（p95 17.88） |
| E8 `editor_ops::diff_replace`（1MB 整篇） | 6.93 |

### 3.2 归因分解

```text
E1 击键帧 40.92
 ├─ 空闲帧（每帧固定工作）                    7.06
 └─ 文本变更引发                             33.86
     ├─ 本项目排版层（拆行/差分/重排1行/concat）  9.24
     ├─ editor_ops::diff_replace               6.93
     └─ 余下（TextEdit 自身 + prev 克隆
              + 最终串重建 + 领域回写）          17.68

裸宿主口径（同一文本、同一宿主，只换 layouter）：
    上游默认 layouter 19.04  ／  本项目逐行 layouter 17.24   →  自家便宜 1.80
应用层净开销（E1 − E7）                       23.67   ←── 占击键帧 58%
```

### 3.3 复现性（三轮独立运行）

| 量 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---|---|---|
| E1 p50 | 40.43 | 40.62 | 40.92 |
| E2 p50 | 9.16 | 8.94 | 9.24 |
| E2b p50 | 0.253 | 0.246 | 0.238 |
| E3 p50 | 21.33 | 18.49 | 19.04 |
| E7 p50 | 17.23 | 16.71 | 17.24 |
| E7 − E3 | −4.10 | −1.78 | −1.80 |
| E1 − E7 | 23.20 | 23.91 | 23.67 |
| 每帧重建行数 max | 1 | 1 | 1 |

E1/E2/E2b/E7 三轮波动都在 ±3% 内；E3（上游默认 layouter）波动较大（18.5~21.3），
故 §4.2 的结论只取**方向**（自家不慢于上游），不给精确差额。

## 4 判读

### 4.1「文本一变即重建 58,514 行 `Galley`」——**证伪**

100 帧连续击键里，每帧真正重排的行数**最大值为 1**；E2 的 20 次独立调用里重建行数取值集合为 `{1}`。
逐行增量缓存（`LINE_LAYOUT` + 内容差分映射）工作完全正常，「整篇重排」从未发生。

§3.2.3 结论 3 那段归因是**错的**：把 39ms 记在「重建 58k 行」上，而实际上重建的是 1 行。
（推测其来源：结论 3 是按 §3.2.2 结论 6 的框架推断的，未与结论 1 的计数证据对账。）

### 4.2「自研逐行排版层是笔负担」——**不成立**

裸宿主下同文本同结构，我们的逐行 layouter **17.24ms** 对上游默认（按段落缓存）**19.04ms**，
自研方案反而便宜 1.80ms（三轮方向一致，见 §3.3）。

⇒ 两点推论：
1. 自研排版层（`highlight_layout.rs` 331 行 + `highlight_cache.rs` 297 行）**是有效的**，不是技术债；
2. **「换成上游默认 layouter」不是一条出路**——它甚至更慢。

### 4.3 真正的成本在应用层，且其中有一处确定性缺陷

`E1 − E7 = 23.67ms` 全部来自 `EditorApp` 在文本变更帧上的额外工作。
其中 `editor_ops::diff_replace` 单项 **6.93ms**，代码级证据（`editor_ops/transform.rs:29`）：

```rust
let old_chars: Vec<char> = old.chars().collect();   // 1MB 文本 → 35 万个 char ≈ 1.4MB
let new_chars: Vec<char> = new.chars().collect();   // 再来一份 1.4MB，外加两遍 UTF-8 解码
...
let byte_start = char_to_byte(old, removed_char_start);  // 内部 char_indices().nth(k) → O(k)
let byte_end   = char_to_byte(old, removed_char_end);    // 再一次 O(k)（k 可达 35 万）
```

`editor_view::show` 在 `response.changed()` 分支里**每击键帧**调它一次。
这与问题 046 的真因「为两个整数付 O(全文)」是同一性质：**diff 只需要字节层的前后缀比较，
却先把整篇字符化了两遍**。1MB 文本上，这两次 `Vec<char>` + 两次 O(k) 扫描就是 6.93ms。
（`char_to_byte` 见 `editor_ops/cursor.rs:6`。）

### 4.4 对「自绘编辑器」决策的影响——收益面被证否

原判定链：`1MB 超限 → 根因是 egui 无虚拟化 → 只能自绘`。
实测链条：`1MB 超限 → 58% 在应用层文本变更链 → 自绘动不到这里`。

再加两条反向证据：自研排版层本就快于上游（§4.2）；且 §3.2.3 的 1MB 数字本身是
「应用层 23.67 + 排版 9.24 + 空闲 7.06」的合成，**没有任何一项需要视口虚拟化才能改善**。

⇒ **结论：1MB 达标不需要自绘编辑器。** 自绘要重写输入事件、编辑状态、绘制、命中滚动
四个层（含 IME 候选窗定位与无障碍），换来的却是一块本来就不是瓶颈的成本。
「是否自绘」应作为独立议题重新评估（收益面只剩「超大文档的可编辑性」这一条产品诉求），
不应挂在 `NFR-PERF-04` 上。

## 5 遗留：余下 17.68ms 尚未拆开

> ⚠ **本节已被 §8~§10 的第二轮测量接管**：17.68ms 已拆到代码行，结论见 §10。
> 下表保留为当时的嫌疑清单（用于对照「猜的」与「量到的」差多少），不再作为待办。

`33.86（文本变更）= 9.24（排版层）+ 6.93（diff_replace）+ 17.68（余下）`。
余下这 17.68ms 的构成本次**未测**，只按代码列出嫌疑清单（按嫌疑排序）：

| 嫌疑 | 位置 | 量级判断 |
|---|---|---|
| `prev = app.editor_text.clone()` | `editor_view.rs:215` | 每帧 1MB 分配+拷贝（空闲帧也做，应已含在 7.06 里） |
| `format!("{}{}{}", &prev[..bs], ..)` 重建最终串 | `editor_view.rs:355` | 每变更帧一次 1MB 分配+拷贝 |
| `editor_ops::transform_insert` | `editor_view.rs:341` | 每变更帧一次（内部可能又扫全文） |
| egui `TextEdit` 在 changed 帧的额外处理 | egui 内部 | E7 已含此项，故应远小于 17.68 |
| 领域 `replace_range` → rope 替换 + 事件发布 | `application/document/service/editing.rs:42` | rope 编辑应 O(log n)，待确认 |

**下一步建议**：先按上表逐项加一次性计时（不必进单测，`--nocapture` 打印即可），
把 17.68 拆到单项 <2ms 为止；优先级最高的是 `transform_insert`（其余项成本可从代码直接估算）。

**优化候选（低风险、确定性收益）**：
1. `diff_replace` 改在**字节层**求前后缀（`as_bytes()` 比较），删掉两处 `Vec<char>` 与两处 O(k) `char_to_byte`
   —— 预计回收绝大部分 6.93ms；
2. `char_to_byte` 若仍需保留，改为按 `char_indices()` 单次推进的共享实现，避免调用方各扫一遍。

1. **余下 17.68ms 未拆开**（§5），故「应用层 23.67ms 里有多少是 egui 造成的」尚无定论；
   但 §4.4 的结论不依赖它——自绘替换的是编辑表面，不改变 `diff_replace` / `prev` 克隆 / 领域回写。
   ⚠ 第二轮已拆开：见 §10.3 的对照表（真正的钱在状态栏的整篇字数统计，占击键帧 27%）。

3. E3/E7 的视口宽度取自裸宿主的 `available_width`，与真实编辑区面板宽略有差异；两者同源，

# 第二轮（049 续）：把余下的 17.68ms 拆到代码行

## 8 实验设计

第一轮的归因把 33.86ms 里的 17.68ms 留成黑盒（§5）。读代码后锁定一批**每帧或每击键一次的
`O(全文)` 操作**，全部位于应用层 / 领域层——即**自绘编辑器照样要付**的那部分。第二轮用
「消融 + 单项探针 + 长度斜率」三种手段把它们量化。

| 组 | 手段 | 被测对象 | 位置 |
|---|---|---|---|
| A2 | **消融** | 同一份代码，只切 `status_bar_visible` | `status_bar_view::show` |
| S1 | 合成 | 整篇 `String` 克隆 | `editor_view.rs:215` 的 `prev.clone()`；`aggregate.rs:394` 的 `snapshot_at` |
| S2 | 合成 | `format!` 重建整篇最终串 | `editor_view.rs:355` |
| S2b | 合成 | 同一路径的另一半：在 `&mut String` 上原地 `insert` | egui `TextEdit` 内部 |
| S3 | 合成 | `line_start_offsets`（2 遍全文扫描 + 58k 项 `Vec`） | `scroll_sync.rs:108`，经 `cursor_line_col` 每帧一次 |
| S4 | 合成 | `line_count`（1 遍全文扫描） | `shared::text.rs:72`，编辑区与状态栏各一次 |
| S5 | 真实链路 | 领域 `replace_range`（含编辑前全文快照） | `service/editing.rs:42` → `aggregate.rs:247` |
| S5b | 同上，10KB | 用长度斜率判定其中 `O(全文)` 成分 | — |
| S6 | 真实链路 | `get_stats` 的 **miss 帧**（整篇克隆 + 全文按行统计） | `service/queries.rs:53`，状态栏每击键一次 |

**为什么 A2 用消融而不是合成**：状态栏的成本不是单一函数，而是「每帧若干次 `O(全文)` 查询
+ 若干次绘制」的合成。合成探针只能逐项估，且 `compute_stats` 是私有函数测不到；消融则
**除状态栏可见性外代码路径完全相同**，差值即该面板的真实总成本，无需假设其内部结构。

**为什么 S6 走真实链路**：`compute_stats` 是 `service/stats.rs` 的私有函数，
只能经 `DocumentAppService::get_stats` 触发；而它平时命中 `(id, revision)` 缓存、
根本不进入统计，故探针里**先做一次编辑把 `revision` 推上去**，强制走 miss 路径。

## 10 判读

### 10.1 最大单块是**状态栏的整篇字数统计**，占击键帧 27%

状态栏每帧调用 `current_stats()` 两次（`sync_goal` 与 `build_model`），缓存键是
`(id, revision)`；击键帧 `revision` 必然变 → **每敲一个键就把 1MB 全文重新统计一遍**。
`compute_stats`（`service/stats.rs:27`）在 1MB 文本上做了**约六遍全文遍历**：

| 遍 | 代码 | 量级 |
|---|---|---|
| 1 | `for raw in text.split('\n')` + 每行 `trim()` + `fence_token_of` + `is_atx_heading` + `task_marker_of` | 58k 行 |
| 2 | `count_links_and_images(text)` | 1MB 逐字节 |
| 3 | `count_words(text)` | 35 万字符逐字符，且西文分支逐字符 `String::push` |
| 4 | `text.chars().count()` | 35 万字符 |
| 5 | `text.chars().filter(!whitespace).count()` | 35 万字符 |
| 6 | `line_count(text)` | 1MB 逐字节 |

这与问题 046「为两个整数付 `O(全文)`」、第一轮 `diff_replace`「为前后缀付两遍字符化」
是**同一类缺陷的第三例**：单次成本不高，但被挂在**每击键**的路径上。

### 10.2 关掉状态栏仍超指标 ⇒ 单修一项不够

`30.43ms` 仍超 16ms 1.9 倍。剩余大头是排版层（9.23）+ `diff_replace`（6.80）+ 空闲帧（7.33）
+ TextEdit 变更路径。**但没有任何一项需要自绘编辑器**：三项分别在应用层、应用层、egui 的
`TextEdit` 内部，而自绘替换的是「编辑表面」这一层——它连 `TextEdit` 都换掉了，
可 §4.2 已证明自研排版不劣于上游、§10.1 又证明最大单块压根不在编辑表面内。

### 10.3 上一轮 §5 的嫌疑清单，对照实测

| 上一轮嫌疑 | 实测 | 判定 |
|---|---|---|
| `prev = app.editor_text.clone()` | S1 = 0.22ms，且**每帧**都做（含空闲帧 7.33 内） | 存在但极小 |
| `format!` 重建最终串 | S2 = 0.37ms | 存在但极小 |
| `editor_ops::transform_insert` | 未单测；1MB 普通击键下只走「单字符插入」分支（`chars().count()==1` 短路 + `matching_close`），不扫全文 | 排除 |

## 13 修复落地：#3 `diff_replace` 字节层（问题 049 的交付）

按 §11 #3 落地。改动点：`src/presentation/views/editor_ops/transform.rs::diff_replace`。

**改前**（1MB 上 6.93ms）：

```rust
let old_chars: Vec<char> = old.chars().collect();   // 35 万 char，约 1.4MB 分配 + 解码
let new_chars: Vec<char> = new.chars().collect();   // 再来一份
// …字符层比较前后缀…
let byte_start = char_to_byte(old, prefix);         // char_indices().nth(k) → O(k)
let byte_end   = char_to_byte(old, n - suffix);     // 再一次 O(k)
```

**改后**（0.24ms）：前后缀在**字节层**比较（不分配、不解码），边界用
`str::is_char_boundary` 回退 / 收拢——UTF-8 自同步，某位置是否为字符边界只取决于
该位置自身是否为续字节，而公共前缀段两侧逐字节相同，故边界判定两侧一致，
无需构造任何字符级缓冲。字符索引只在前缀处算一次，
光标 =「前缀字符数 + 插入内容字符数」。

| 量 | 改前 | 改后（三轮独立运行） |
|---|---|---|
| `diff_replace` 文末追加（前缀最长 = 最坏位置） | 6.93 | **0.24 / 0.25 / 0.24** |
| `diff_replace` 文档中点替换 | ~6.9（旧实现与位置无关） | **0.33 / 0.33** |
| 1MB 击键帧 p50（E1） | 40.43 / 40.62 / 40.92 | **34.55 / 33.73 / 35.48** |
| 1MB 击键帧 p95 | 43.42 | **37.41 / 36.12 / 38.56** |
| 1MB 同运行空闲帧 | 7.06 | 7.32 ~ 7.65 |

改后三轮的 E1 区间 **33.7~35.5** 与改前的 **40.4~40.9** 无重叠，差额 5.4~6.4ms；
与 `diff_replace` 的绝对降幅（6.7ms）同量级 —— 交叉印证。

**四条判读**

1. **单次调用提速约 27×**（6.93 → 0.24ms），击键帧同步降 6.4~7.2ms——降幅与该项的
   绝对降幅一致，反证这笔钱确实全部出自 `diff_replace`（不是巧合的噪声）。
2. **位置敏感度消失**：旧实现无论改哪里都要整篇字符化（恒 6.9ms）；新实现只在
   **前缀处**做一次字符计数，文末 0.24 / 中点 0.33——量级恒定。
   （注意：文末追加恰恰是前缀**最长**的最坏位置，不是有利位置；中点略高属噪声。）
3. **对外语义零变化**：`TextEdit` 各字段逐字段等同旧实现——由
   `diff_replace_matches_char_level_reference` 以旧实现为基准对照 16 组输入，
   含中文、4 字节字符、以及公共前后缀落在字符中间（`café`↔`cafè`、`é`↔`Ã©`）。
4. **剩余缺口未变**：1MB 仍超 16ms 2.3×，大头是状态栏整篇统计（9.30ms）+ 排版层
   （9.09ms）+ 空闲帧（7.5ms）——即 §11 的 #1 / #2 待办，均在应用层。

**守卫**：`editor_ops.rs` 三条边界单测 + 归因用例的「两位置均 < 2ms」量级断言。
变异验证：去掉两处 `is_char_boundary` 调整 → 三条单测立即全部 panic 在非字符边界切片上。

### 14.3 建议二详解：「排版层 9.1ms」里约 6.6ms 是自家簿记（微基准实测）

E2（`mapper::highlight_layout_with_find`，文本变 1 字节）实测 **9.24ms**。读代码可见它在
**整文档缓存 miss**（= 每次击键）时要走完整条路，沿途有 **4 次 O(全文) 复制 + 3 轮
O(行数) 堆分配**（1MB ≈ 58,514 行）。把每一项单独量出来（`rustc -O`，1MB / 58,514 行）：

| # | 位置 | 动作 | 微基 |
|---|---|---|---|
| ① | `:98` | `WHOLE_CACHE.with(\|c\| c.borrow().clone())`——**`Ref<T>` 不实现 `Clone`**，故这里真的在复制整个条目（含 1MB `String`） | **0.23ms／每次调用**（含空闲帧） |
| ② | `:100` | `cached_text == text` | 0.03ms |
| ⑥ | `:114` | `text.split('\n').collect()`（58,514 项 `Vec<&str>`，约 936KB） | 1.17ms |
| — | `:161~191` | `reuse_map` 建表 + 前后缀 58,514 次行比较 | ~0.7ms（估） |
| ④ | `:149` | `c.lines.clone()`——上一版 `Vec<String>` 克隆 = **58,514 次小堆分配** | **2.47ms** |
| ③ | `:270` | `c.lines = lines.iter().map(to_string).collect()`——**又是 58,514 次小堆分配** | **2.29ms** |
| ⑤ | `:271` | `c.galleys = line_galleys.clone()` + `:193` | 0.44ms |
| — | `:309~314` | `job.append(text)` 写全文 + `Galley::concat` clone `job`（又两次 1MB） | ~0.4ms |
| — | `:319` | `text.to_string()` 存回整文档缓存 | 0.23ms |

③+④+⑤+⑥ 合计 **6.37ms**，加 ①/②/`to_string` 共约 **6.6ms**——**占 E2 实测 9.24ms 的 71%**。
账目对得上，说明这 6.6ms 不是 egui 的，而是**本项目缓存簿记的重复劳动**：

- `:270` 重建的那 58,514 个 `String`，其中**绝大多数行的内容与上一版逐字节相同**
  （`reuse_map` 已经算出哪些行没变），却被整体重新分配了一遍；
- `:149` 又把上一版整份克隆一遍——两份都在做同一件事。

**改法（不动 egui、不改对外语义）**

1. `:98` 的整条克隆改为「在借用内比较、只把 `Arc<Galley>` 取出」；缓存的文本改为
   `Arc<str>` 共享（或 `(len, hash)`），消掉每帧一次的 1MB 复制 + 每击键一次的 `to_string`。
   ⚠ 若改用哈希，须评估「碰撞 → 残留旧字形」的风险是否可接受（本项目的确定性纪律偏保守，
   建议优先 `Arc<str>`）。
2. `:149` 改 `mem::take` 语义——把上一版**移出**而不是克隆，用完写回。
3. `:270` 改为**原地重建**：`reuse_map[i]` 命中则复用上一版的 `String`（移动），
   只有真正重排的行才新建——把 58,514 次堆分配降到「每击键 1 次」。
4. `:271` / `:193` 的行 `Galley` 列表改存 `Arc<[Arc<Galley>]>`，与 `concat` 共用同一份。

### 14.4 不建议做：自绘编辑器（结论不变，理由更硬）

自绘替换的是**编辑表面 + 排版**两层，而三轮实测显示 1MB 击键帧的成本大头都在它之外：

- 状态栏整篇统计 9.3ms——应用层，自绘无关；
- 排版层 9.1ms 中约 6.6ms——**本项目自己的缓存簿记**，自绘无关；
- `diff_replace` 6.8ms——应用层，**已修**（§13）；
- 仅剩「`TextEdit` changed 路径」与零星项，且同一裸宿主下**自家排版比上游默认排版还快**
  （§4.2：17.24 vs 19.04）。

故 §0 那句「要达标只能自绘」不仅缺证据，现在还有反证：**把自家簿记修掉就能收回 6.4ms**。
「是否自绘」应作为**独立议题**（若真做，收益面只剩「超大文档的可编辑性」）重新评估，
不要挂在 `NFR-PERF-04` 上。

### 14.5 需要裁定的口径问题：`NFR-PERF-04` 的 1MB 档

现状 1MB p95 36~38ms，超 2.3×。两条路：

- **A（建议先取）**：明确 1MB 档为**尽力而为**——指标覆盖 ≤100KB（已达标），1MB 档
  写进 README 已知限制与 `docs/spec/metrics.md` §3.2.3 的口径声明；守卫阈值按档位
  （10KB/100KB 守 16ms，1MB 守数量级，现状已如此）。
- **B**：真要让 1MB **硬达标**，需要视口虚拟化；而 `layouter` 接口**拿不到滚动位置**

  编辑视图，成本远超本期。且按 §14.3，B 能省下的那部分**大头还没兑现**（先修一/二再看缺口）。

建议：先取 A；把 B 与「是否自绘」合并为同一议题另行评估。

### 14.6 落地顺序建议

先后次序不是按收益大小，而是按**相互依赖**：

1. **建议四**（零散项，~1.5ms）：都是小幅、局部改动，先把帧路径的「恒定开销」压平，
   便于后续测量归因（否则每次改完都要在 1.5ms 噪声里辨认效果）。
2. **建议一**（状态栏统计，~9.3ms）：收益最大且风险最低；两处同帧调用要**共享一次结算**

3. **建议二**（排版层簿记，~6.4ms）：收益次大但要动缓存键语义，须配等价性对照

4. **建议三**（统计单遍化，停手帧 −4~6ms）：可与建议一合并提交（同一函数、同一风险面）。

### 14.7 附：§14.3 微基准探针源码

单文件、无依赖，`rustc -O probe.rs -o probe && ./probe` 即可复现（Windows 用 `probe.exe`）。
测的是 stdlib 语义级开销，用于**把「整篇复制 / 逐行分配」从端到端耗时里摘出来**；
端到端验收仍以 E2 与击键帧为准。

```rust
use std::sync::Arc;
use std::time::Instant;

const LINES: usize = 58_514;

fn bench(name: &str, n: usize, mut f: impl FnMut()) {
    for _ in 0..20 { f(); }                       // 预热
    let t = Instant::now();
    for _ in 0..n { f(); }
    println!("{name:<44} {:>8.4} ms", t.elapsed().as_secs_f64() * 1000.0 / n as f64);
}

fn main() {
    let line_len = (1024 * 1024) / LINES;
    let text: String = (0..LINES).map(|_| "x".repeat(line_len)).collect::<Vec<_>>().join("\n");

    // ① `Ref<T>` 不实现 `Clone` ⇒ 这里复制的是**整个条目**（含 1MB String）。
    let cell = std::cell::RefCell::new(Some(text.clone()));
    bench("① WHOLE_CACHE clone（含 1MB String）", 2000, || {
        let b = cell.borrow();
        let c: Option<String> = b.clone();
        std::hint::black_box(&c);
    });

    let other = text.clone();
    bench("② 1MB String == 比较", 5000, || { std::hint::black_box(text == other); });

    let lines: Vec<&str> = text.split('\n').collect();
    bench("③ 58.5k 行 String 全量重建（:270）", 200, || {
        let v: Vec<String> = lines.iter().map(|s| (*s).to_string()).collect();
        std::hint::black_box(&v);
    });

    let owned: Vec<String> = lines.iter().map(|s| (*s).to_string()).collect();
    bench("④ 上一版 Vec<String> 克隆（:149）", 200, || { std::hint::black_box(owned.clone()); });

    let galleys: Vec<Arc<u32>> = (0..LINES).map(|i| Arc::new(i as u32)).collect();
    bench("⑤ 58.5k 次 Arc 克隆（:271）", 2000, || { std::hint::black_box(galleys.clone()); });

    bench("⑥ split('\\n').collect()（:114）", 2000, || {
        let v: Vec<&str> = text.split('\n').collect();
        std::hint::black_box(&v);
    });
}
```
