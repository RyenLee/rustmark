### 3.2 F-3 远程图片同步加载阻塞 UI 线程 → 异步化

`presentation/views/preview_view.rs`：

- `ImageEntry` 加 `loading: bool` + `ImageEntry::loading()`；
- `REMOTE_INFLIGHT` thread_local `HashSet`：同一 URL 不重复 spawn 下载线程；
- `RemoteChannel`（`OnceLock` + `Sender` + `Mutex<Receiver>`）：后台线程下载完成回执；
- `spawn_remote_load<L: FnOnce(&str) -> Result<LoadedBytes, String> + Send + 'static>`：
  闭包捕获 `app.services.assets` 的 **Copy 值**（分层规避：presentation 不得 import
  infrastructure，用 Copy 字段推断 + 泛型闭包传递 AssetLoader）；
- `drain_remote_results(ctx)`：收干回执 → UI 线程 `load_texture` → 入缓存 → `request_repaint()`；
- `image_entry` 重排：drain → 缓存命中 → remote 则 spawn + loading 占位 → 否则原同步路径；
- `media.rs`：`None if entry.loading` 分支输出「图片加载中：{alt}」占位，高度与失败占位一致
  （保滚动同步）；
- `ImageCache` 内件改 `LruMap`（D-4 后）；
- 公开 `is_remote_url()` / `image_cache_state()` / `ImageEntryState` 供测试；
- **3 个测试**：URL 分类、`10.255.255.1`（不可达 IP）证明首绘不等网络、`127.0.0.1:1`

## 4. 批次 D：可维护性与微优化

### 4.1 D-4 LRU 泛型抽取（四处同构实现收敛）

**新增** `shared/lru.rs`：`LruMap<K, V>`（ahash + 访问序 `Vec`）。

契约（四处原实现逐条对齐，勿随意更改）：

1. 容量至少为 1（`new(0)` 按 1）；
2. 驱逐只发生在「已满且插入新键」时；**覆盖已有键永不驱逐**且刷新访问序；
3. 命中即挪到序尾；**条件命中**（版本号/语言/区间判定）用 `peek` + `touch` 两步，
   避免未命中的查询污染访问序（否则陈旧键被一次次续命、永不被驱逐）；
4. `entries` 与 `order` 键集恒一致：所有写路径经 `insert` / `invalidate` / `invalidate_all`；
5. 查询方法 Borrow 泛型（`K = String` 可直接传 `&str`），`move_to_back` 用「取出再压回」
   零克隆。

迁入方：`markdown/service/spell_cache.rs`、`render_cache.rs`、`highlight_cache.rs`
（`HighlightPace` 刻意保留 ahash HashMap + 任意淘汰，它是节流器不是缓存）、
`presentation/views/preview_view.rs` 的 `ImageCache`。
三处缓存原 `#[derive(Default)]` 删除（核实全仓零使用）。

**7 个新单测**：LruMap 6（驱逐最旧非任意、覆盖不驱逐且刷序、peek 不续命、
peek+touch 条件命中、invalidate 两表同步、容量下限 1）+ spell_cache 1
（陈旧查询不得续命）。其中 `invalidate_removes_from_order_too` 的断言形式经过一次修正：
最初断言写错容量；最终版用「不同步会让缓存超出容量上限（`len() > capacity`）」作为症状断言，
比单纯断言 get 结果更能抓住两表漂移。
