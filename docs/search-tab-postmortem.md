# 技术复盘：侧边栏「搜索」标签严重卡顿

> 状态：**已修复并验证**（2026-10-23）
> 详细排查过程见 [`search-tab-performance-report.md`](./search-tab-performance-report.md)；数字口径见 [`metrics.md`](./metrics.md) §3.2.14；回归门禁见 `tests/presentation/search_perf_test.rs`。

---

## 1. 问题概述

| 项 | 内容 |
|---|---|
| 现象 | 侧边栏切到「搜索」标签后整窗冻结；在输入框打字逐字卡顿；鼠标划过侧栏、滚动结果列表也会卡 |
| 触发条件 | 搜索标签**可见**（未折叠）**且**查询框非空（`SidebarUiState::should_search()`）。此状态下**每一帧**都重算搜索 |
| 影响范围 | 所有工作区，卡顿程度随**文件数线性放大**；查询为空时无开销，因此表现为「一打字就卡」 |
| 严重度 | 高——千文件工作区下切换首帧约 160–290 ms（release），交互完全不可用，远超 100 ms 预算 |

## 2. 时间线

1. **现象确认**：切到搜索标签（查询非空）即卡顿，与文档大小关系弱、与工作区文件数强相关——第一个指向「读盘」的信号。
2. **全链路追踪**：`main_view::show → sidebar_view::show → search_tab → count_hits / 结果列表 → EditorApp::search_workspace → WorkspaceAppService::search → gather_candidates → FsWorkspaceRepository::read_content → fs::read + 解码`。
3. **分段计时定位**：为三段打点（单次 `search_workspace` / 侧栏整帧 / 切换首帧），外加两组「旧实现等价成本」对照（一帧两次搜索、逐文件读盘）。
4. **根因锁定**（详见 §3）：范围过滤与读盘错序 + 一帧两次全量搜索 + 搜索内核的分配与重复扫描。
5. **修复与门禁固化**：三处修复 + `search_perf_test.rs` 性能门禁，全量 2107 个用例通过。

## 3. 根因分析

### R1（主因）：「当前文档」范围把范围过滤放在读盘之后

`WorkspaceAppService::search` 对默认的「当前文档」范围传 `include_disk = true`，于是 `gather_candidates` **先把整个工作区逐文件 `fs::read` + 编码探测读进内存**，再用 `candidates.retain(|(id, ..)| *id == active_id)` 丢弃除目标外的一切——读到的内容当场扔掉。

- 代价：**81–146 ms/次**（1001 文件，release，冷热缓存决定），与活动文档大小**无关**；
- 最讽刺的是，函数文档写的是「过滤放在候选收集之后、读盘之前」——**注释与实现相反**，这正是缺陷长期未被发现的原因：读代码的人（和写文档的人）都以为过滤早于读盘。

**5-Why**：

1. 为什么卡？→ 每帧搜索要读整个工作区的文件。
2. 为什么读整个工作区？→ 「当前文档」范围也传了 `include_disk = true`。
3. 为什么不单取目标文档？→ `gather_candidates` 没有 `only_document` 形参，只能先收集再过滤。
4. 为什么设计成「先收集再过滤」？→ 「打开的文档」范围确实需要全部打开文档，「当前文档」被顺手塞进了同一条路径。
5. 为什么没被测试拦住？→ 功能用例只断言「结果对不对」，工作区只有几个文件时读盘开销不可见；没有性能口径的门禁。

### R2：同一帧跑两遍全量搜索

开关行右侧计数调一次 `count_hits`（内部 `search_workspace`），下方结果列表又调一次。**成本 ×2**，且两次结果来自不同时刻，计数与列表可能不同源。

### R3：搜索内核的分配与重复扫描

- 大小写不敏感比较：每次字符试配 `to_lowercase().collect::<Vec<char>>()` **分配两个小 Vec**，1MB 文档按字符逐一试配即数十万次堆分配；
- 求每条命中的行号：`text[..start_off]` 数换行 + `rfind` **重扫全文**，50 条命中 = 50 遍全文（O(命中数 × n)）。

### 已排查并排除的项

| 排查项 | 结论 |
|---|---|
| 重复组件挂载 / 全量重渲染 | 无——标签分派只走一个分支；但存在 R2 的「重复计算」 |
| 结果列表无虚拟列表 | 非瓶颈——egui 即时模式渲染增量实测 0.0–0.2 ms，300 条硬上限兜底 |
| 高频事件未防抖 | 搜索框只有 `changed()` 回写，无每字符订阅；真正问题是「任何重绘都无条件重算」（R1 消除后单帧成本已进预算，未再加短路） |
| 内存泄漏 / 未清理定时器、订阅 | 无——该路径不注册定时器、不订阅事件，结果 ≤300 条，无跨帧增长 |
| 重复接口请求未取消 | 本应用无网络请求；等价物是同步磁盘 IO，已由 R1/R2 消除 |

## 4. 修复方案

| 文件 | 改动 |
|---|---|
| `src/application/workspace/service.rs` | `search`：`include_disk = only_document.is_none() && !only_open_documents`——**范围过滤与读盘由同一个判断决定**，从结构上杜绝「读完再丢」；`gather_candidates` 新增 `only_document` 形参，该范围按 id 单取目标文档全文，不再为其余打开文档做全文快照 |
| `src/application/workspace/service.rs` | `search_text`：新增 `char_eq_ignore_case`（ASCII 走 `eq_ignore_ascii_case`，其余 `to_lowercase().eq()` 迭代器比较，**零分配**）；行号/行首改为**跨命中增量**统计，总复杂度 O(n)，替代 O(命中数 × n) |
| `src/presentation/views/sidebar_view/search.rs` | `toggle_row` 返回本帧**唯一一次**搜索结果，计数与列表**同源复用**；删除 `count_hits` |
| `src/app/frame/outline.rs`、`sidebar_view.rs` | 修正与实现不符的文档注释（原注释声称的「先过滤后读盘」正是缺陷本身） |
| `tests/presentation/search_perf_test.rs` | 新增性能门禁（见 §6） |

设计取舍：**不引入结果缓存**——仓库纪律是「搜索结果不在 UI 状态里缓存」（否则易出现「文件改了、结果还是旧的」）；R1–R3 修完后单帧已进预算，缓存只会新增一类失效缺陷。**不引入虚拟列表**——渲染增量实测可忽略，不值当打散分组渲染。

## 5. 性能对比数据（release / Windows x86_64）

| 场景 | 修复前（等价成本） | 修复后 | 提升 |
|---|---|---|---|
| 1001 文件工作区 · 「当前文档」单次搜索 | **81–146 ms** | **0.00 ms** | 不再读盘 |
| 1001 文件工作区 · 切到搜索标签首帧 | **≈160–290 ms**（2 × 单次） | **0.69 ms** | **≈250×** |
| 1MB 文档 · 50 条命中 · 整帧 | 11.5–11.7 ms（两次搜索） | **6.0–6.4 ms**（p95 6.5） | **≈1.9×** |
| 1MB 文档 · 切到搜索标签首帧 | ≈11.5 ms | **6.2 ms** | **≈1.9×** |
| 侧栏「文件」标签整帧（对照组） | — | 0.03 ms | — |

**验收结论**：「切到搜索标签后交互响应 < 100 ms」——千文件工作区 **0.69 ms（145× 余量）**，1MB 文档 **6.2 ms（16× 余量）**；debug 口径同向（1MB 整帧 27.1 → 11.9 ms）。

## 6. 验证与门禁

- 复现命令：`cargo test --release --test presentation -- search_perf --nocapture`
- 门禁断言（`tests/presentation/search_perf_test.rs`）：
  - 「当前文档」单次搜索 < 10 ms（两档均断言；旧实现 81 ms 起，任何重新读盘都会顶破）；
  - 切到搜索标签首帧 < 100 ms（release 断言，debug 仅打印——沿用 `metrics.md` §3.2.10 的口径约定）。
- 回归：`cargo test` 2107 个用例 0 失败；`cargo fmt --check`、`cargo clippy --all-targets` 干净。
- 说明：Windows 下 `perf`/WPA 需要管理员 + ETW，且本缺陷是**确定性同步阻塞**，火焰图只会反复显示同一栈；故采用可复现的帧内分段计时，等价于 scope 采样且能长期进 CI。

## 7. 经验教训

1. **「先取全集再过滤」在读 I/O 路径上是反模式**。过滤条件必须与 I/O 决策由**同一个判断**产生；拆成两步，注释写得再对，实现也会漂移。本次缺陷的注释与实现直接相反且长期无人发现，就是因为二者没有代码层面的强绑定。
2. **注释不是规格**。本项目习惯以注释承载设计意图，但注释描述了不存在的行为 = 负资产。修复时已把该段注释重写为与 `include_disk` 判断同址的说明。
3. **功能用例看不见性能**。结果正确 ≠ 可接受：1000 个文件下搜索结果依然全对，只是要 81 ms。**性能必须有独立门禁**，且阈值要卡在「旧实现必破、正常波动不破」的位置（10 ms vs 81 ms，7× 余量足够抗抖动）。
4. **「成本 ×N」类缺陷容易藏在 UI 层**。应用层测试永远看不到「同一帧调了两次」——只有整帧级的分段计时能暴露。计数与列表同源复用不仅省一半，还消除了「计数与列表不一致」的潜在正确性问题。
5. **测量口径优先于工具执念**。没上火焰图不是偷懒：确定性同步阻塞 + 可复现分段计时，后者结论更强且可回归。选工具的标准是**能否长期防复发**，不是是否「专业」。
