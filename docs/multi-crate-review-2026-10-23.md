## 一、核心优势与存在不足（结构化优缺点分析）

### 1.1 核心优势

| # | 优势 | 证据 | 价值 |
|---|---|---|---|
| A1 | **反向依赖从「规则」升级为「不可能」** | core → root 的依赖被 cargo 编译期锁死（`cargo tree` 验证）；D-11 的「组合根不可被下层反向依赖」此前仅靠词法校验 | 架构规则的强制力上了一个量级：词法校验能拦 `use`，cargo 能拦**一切** |
| A2 | **crate 边界与 DDD 装配边界重合** | shell 独占 eframe（窗口运行时）、wgpu（渲染后端）、anyhow（编排错误）、env_logger（日志后端）——全是「进程装配」关注点；业务关注点全部在 core | 拆分线不是随意的文件搬家，而是「装配 vs 业务」的语义线 |
| A3 | **改造成本接近零（路径零改动）** | root 以 `lib.rs` / `presentation.rs` 两处 `pub use` re-export 拼接，git diff 中迁移文件大量 100% rename；340 处字段读点、全部存量测试零改动 | 63k 行项目的物理拆分未产生行为回归（2125 测试全绿） |
| A4 | **增量构建方向正确** | 改视图 4.7s vs 改 core 6.6s：高频改动侧（views/app）不触发 core 重编；core 改动只向下游扇出一次 | 视图迭代是日常高频路径，其增量成本被隔离在 shell |
| A5 | **校验器同步进化，无「检查盲区」** | `scan_project` 三根扫描（shell src + core src + tests）、归一化堵死 `rustmark_core::` 前缀绕过、manifest 级豁免登记 | 拆分没有削弱既有的「规则→机械检查→CI」闭环，反新增了双拼写防绕过 |

## 二、多 crate 现状专项评审

> 题设：「DDD 范式下，原本单个独立 crate，后续新增拆分出多个 crates」——这是典型的
> **后验治理式拆分**（先长成 63k 行、表现层占 49%，再拆边界），而非预防性设计。

### 2.1 DDD 领域边界划分的合理性 —— **拆分线选「组合根」而非「限界上下文」，是正确选择**

**现状**：5 个限界上下文（Document / Markdown / Workspace / Preferences / Export）全部留在
core 内部的**目录级**边界（`domain/{document,markdown,workspace,preferences,export}/`），
crate 粒度只体现了一条线：**组合根+视图（shell） vs 其余（core）**。

**评审结论：正确，且是本方案最关键的一步走对了。** 理由：

1. **application 层天然跨上下文**。上下文映射（Document→Markdown Customer-Supplier、
   Document↔Workspace Shared Kernel、Workspace→Document ACL、Preferences→全部 Published
   Language）决定了用例编排必须同时触碰多个上下文。按上下文拆 5 个 domain crate 会立刻
   把 `application` 与 `shared` 的归属切碎：要么造出一个「application 巨型 crate」使拆分
   失去意义，要么上下文间出现 N×N 依赖图。
2. **shared kernel 无处安放**。`DocumentId` 等共享内核被拆分后要么复制（违反单一真源）、
   要么独立成第 3 个 crate（为尚不存在的复用需求付费）。
3. **收益无法兑现**。DDD 上下文独立拆分的核心收益是**独立演进/独立部署**——本项目是
   单机单进程桌面应用，无独立部署诉求；拆了只有成本没有对价。
4. **拆分线语义扎实**（优势 A2）：shell 独占的恰是进程装配关注点（eframe/wgpu/anyhow/
   env_logger），core 收拢全部业务关注点。这条线与「组合根是唯一允许依赖全部层的地方」
   （约束 §1）严格对应——**crate 边界就是组合根的物理化**。

**遗留缺口**：上下文边界仍是目录约定（B3）。这不是当前的错误，而是需要**监控项**
（何时再拆，见 §4.3）。

### 2.2 crate 之间的依赖关系 —— **极简 DAG，三层强制叠加**

```
rustmark (shell)
   │  eframe / wgpu / anyhow / env_logger（进程装配关注点独占）
   └──► rustmark-core（13 个直接依赖）
            │  内部：presentation → application → domain ◄── infrastructure
            │        （shared 为零业务内核，词法级 check-arch 强制）
            ✗  cargo 锁死：core 永远无法依赖 shell
```

- **物理层（cargo）**：反向依赖编译不可能，`cargo tree -p rustmark-core` 输出仅自身；
- **词法层（check-arch）**：core 内部五层间 + presentation 六子模块间的禁令矩阵，
  含 `rustmark_core::` 前缀归一化防绕过；
- **规约层（constraints 文档）**：依赖矩阵 §3、禁 crate 表 §4、判定口径 §4.1。

**评价**：两节点、单边、无环的依赖图是多 crate 方案能拿到的最简形态；三层管控分别
拦截「物理不可能 / 路径引用 / 设计意图」，冗余但各管一段，与本项目「规则必须被机械
执行」的治理传统一致。**依赖维度无风险。**

### 2.3 模块内聚与耦合程度

| 对象 | 内聚评价 | 耦合点 |
|---|---|---|
| core（247 文件） | **高**：DDD 五层各司其职，层内按上下文/子模块分目录；无跨层环（审查报告 §3.2 实测） | 层间依赖单向且被三层强制；残余耦合是上下文间共享内核（DDD 的合法耦合） |
| shell（82 文件） | **高**：只剩组合根 + 视图 + 2 个拼接点，职责单一 | 视图经 `&EditorApp` 状态句柄下行（获认可通道，32 文件 `use crate::app::frame`）；C-2 状态穿透、C-3 胶合为词法管控（B7） |
| 拼接点本身 | — | `pub use` re-export 是**有意的耦合债**：把「路径兼容」换成「读者需理解拼接」（B2）。用 2 个文件的可读性代价换 340+ 读点零改动，交易划算 |

**净效果**：耦合总量没有减少（拆分不消灭依赖，只使其显式化），但**耦合的可违约性**
大幅下降——最危险的「下层反向依赖组合根」从可违约变成不可违约。

### 2.4 开发体验（DX）

| 正面 | 负面 |
|---|---|
| `cargo test -p rustmark-core` 可独立跑核心 357 单测，迭代回路更短 | 新人需理解 workspace、双 crate、拼接点三件事才能看懂一条路径 |
| check-arch 报告带 `crates/rustmark-core/src/` 前缀，违规定位到 crate | `crate::` 与 `rustmark_core::` 双拼写并存，跳转/搜索需两边都查 |
| rust-analyzer 双 crate 正常工作；IDE rename 跨 crate 边界由编译器校验 | shell 内文件的 `crate::presentation::state` 实际可能落在 core——路径心智多一层 |
| 改 UI 与改业务的文件区不重叠，并行 agent/开发者冲突面小 | 命令面新增 `--workspace` 心智（忘带静默缺席，B4） |
| 迁移零手术：存量 `use crate::` 全部照旧工作 | 拼接点文件本身是「魔法」，不读 constraints §7 看不懂 |

**评价**：DX 成本集中在**首次理解成本**（一次性），收益是**日常回路成本**（持续性）。
对熟悉 DDD 与 cargo workspace 的贡献者，学习曲线约 10 分钟。

### 2.5 构建效率 —— **实测无回归，增量方向正确**

| 场景 | 实测 | 解读 |
|---|---:|---|
| `cargo check --workspace --all-targets` 无变更 | **0.4s** | 指纹校验，workspace 化无额外开销 |
| 改 shell 视图一处 | **4.7s** | core 全程缓存命中——**高频迭代路径不为拆分付费** |
| 改 core 一处 | **6.6s** | core 重编 + root 下游扇出；比视图路径多 1.9s |
| release 全量构建 | 1m22s | 单 target 目录共享，egui 等公共依赖**不重复编译** |
| 产物体积 | 10 485 248 B | 拆分不改变链接结果，仍在 10MB 红线内 |
| 全量测试 | 2125 通过（约 75s 热） | 与拆分前（2101）同量级，+24 为新增用例 |

**评价**：双 crate 的理论代价（重复编译公共依赖、两套指纹）在单一 `target/` 下基本不成立。
拆分后最坏路径（改 core）也只比最好路径（改视图）多约 2s。**构建效率维度无风险**，
建议将上述三个计时数字作为基线留档（§4.6）。

## 四、架构优化建议与风险规避

### 4.1 [立即·高价值·零成本] 用 `default-members` 把 `--workspace` 纪律机制化

根 `Cargo.toml` 的 `[workspace]` 段增加：

```toml
[workspace]
members = [".", "crates/rustmark-core"]
# 不带 --workspace 的裸 cargo test / check / clippy 也覆盖两个成员，
# 消除「忘带 flag → core 单测静默缺席」（债务 D-2 当场清偿）
default-members = [".", "crates/rustmark-core"]
```

CI 的 `--workspace` 保留（双保险）；约束文档 §6 的「必带」改注为「已由
default-members 兜底，`--workspace` 仍显式书写以自明意图」。

### 4.2 [已完成 2026-10-23] 执行 4b：可见性收紧（D-1）

> **执行结果**：五批独立提交（domain 2995d68 → application 15e9020 → infrastructure a24b5ca
> → presentation e21ad8c → 字段级 2952872），每批全链验证后独立提交，未与功能改动混批。
> 模块级 `pub` 项 1 664 → 1 383，字段级 `pub` 606 → 547（58 处收紧为 `pub(crate)`、
> 1 死字段删除、547 对读点/构造点逐条核对后保留——方案初估 340，编译器实测 E0616/E0451
> 报出 547 对）；`pub(crate)` 13 → 282 行。白名单守卫 `tests/field_visibility_guard_test.rs`
> （548 条 pub 字段 + 集合相等双向断言 + 3 条注入用例）把「放宽回 pub」这个编译器沉默
> 的方向也钉死。全链验证：fmt / clippy -D warnings / check / check-arch /
> test 2 129 执行 2 125 通过 0 失败 4 忽略 / release 构建冒烟 OK。

原方案（获批后置条件）：

1. **顺序**：`domain` → `application` → `infrastructure` → `presentation/state|theme|widgets|rich|icons|shortcuts`
   （越靠下越先收紧，编译器报错即读点清单）；
2. **字段级**：aggregate/VO 的 `pub` 字段 → `pub(crate)` + 受控方法，对照 340 处读点
   逐字段核对，复用阶段 2 的白名单清单测试模式；
3. **出口**：核心聚合仅暴露 application 所需接口，shell（views）只经 DTO 与状态句柄；
4. **纪律**：单独批次、不与任何功能改动混批、每批全链验证 + 独立提交。

**收益（已兑现）**：core 的 pub 面收缩到真实接口面（模块级项 1 664 → 1 383、字段 606 → 547），
D-11 的 core 侧编译期强制至此完整闭合；
「core 内部重构」对 shell 从「惯例上不碰」变成「编译上碰不了」。

### 4.3 [监控] 再拆的触发条件——预防性拆分是本方案最大的未来风险

**默认不拆**（D-5）。出现以下**任一**信号时，才启动下一轮拆分评审：

1. 某上下文需要**独立部署或进程隔离**（如 Export 转后台服务、渲染转 WASM 前端）；
2. 某上下文需要引入**重依赖且不愿让全仓背编译成本**（且无法以 feature 解决）；
3. **跨上下文变更占比**持续 > 40%（改动总落在 ≥2 个上下文的同一 PR），说明目录边界
   已不足以约束耦合；
4. 出现**第二个可复用消费者**（第二个二进制/ crate 需要 domain 层）。

反向红线：**不为「DDD 更纯粹」拆分**——按限界上下文拆 5 crate 已被 §2.1 证伪。

### 4.4 [近期] 双拼写收敛口径（D-4）

- **存量不动**（`crate::` re-export 路径继续有效，校验器归一化永久保留）；
- 写入约束文档 §4.1 一句：新 shell 代码两种拼写均可（语义等价），但**同一文件内保持
  一致**；core 内永远只有 `crate::`（反向依赖已被 cargo 锁死）。

### 4.5 [近期] 测试归属口径入约束（D-6）

在 `architecture-constraints.md` §9 增补一条：

> core 的纯单元测试随实现入 `crates/rustmark-core/src/**`；跨边界契约与端到端测试
> 一律在 root `tests/`（消费者视角，R-02）；root 测试**不得**直接断言 core 私有实现
> （4b 已收紧，现由编译器强制）。

### 4.6 [持续] 构建效率守门

本次实测三个数字（0.4s / 4.7s / 6.6s）留作基线。建议：CI 的 check 步骤若耗时相对
基线漂移 > 50%，先查是否有人绕过 `default-members` 或新增了全仓生效的
`RUSTFLAGS`/`build.rs`。体积红线（10MB）已有门禁，无需新增。

## 五、结论

1. **优缺点**：7 项核心优势（依赖不可能化、装配边界语义化、零手术迁移、增量方向正确、
   校验无盲区、CI 口径统一、协作面分割）显著大于 7 项不足（全部为「完成度/纪律」类，
   无方向性错误）。
2. **专项评审**：拆分线选组合根而非限界上下文，是本方案最关键的正确决策；依赖图为
   两节点单边 DAG，三层强制叠加；两侧内聚高、耦合显式且可控；DX 成本是一次性的，
   构建实测无回归。
3. **技术债**：**方案本体不构成债务（正资产）**；遗留项合计**中低**等级——主债 4b
   可见性已清偿（2026-10-23 五批完成）、`--workspace` 纪律（中，一条配置清偿）、
   app↔views 词法管控（中，存量）+ 4 项低风险项，无高危。
4. **建议**：§4.1 执行（清偿 D-2）、~~§4.2~~ 已执行（清偿主债 D-1）、§4.3 作为
   未来拆分的否决框架、§4.4-4.6 为口径与守门补丁。按此执行，该架构可支撑业务中长期
   演进而无需结构性返工。
