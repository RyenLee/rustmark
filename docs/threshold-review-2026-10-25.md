# 阈值合理性评估（2026-10-25）

评估对象：`docs/threshold-audit-2026-10-25.md` 收录的 115 项阈值（基线提交 `574b946`）。

> **2026-10-25 晚更新**：§7 的 P0/P1 已落地，实施记录、门禁数字与偏差说明见 **§11**。
> §0–§9 保留评审时点的事实与判断，不回改历史结论。

## 0. 结论

**判定：单点取值大体合理，体系约束不完全合理。**

- **约 90 项（78%）判定为合理，建议保留**。核心交互阈值（150ms 防抖、IME 800/50ms、分栏与侧栏边界、滚动抑制、拼写距离、导出上限）依据明确、有实测或规范支撑，不属于「拍脑袋数字」。
- **约 25 项需要调整**，但不是零散失准，而是集中在 6 个语义簇：体积门禁、大文件阈值、150ms 防抖、图片资源、搜索/文件树上限、字号档位。每一簇的共性是「同一语义多份副本」或「计价单位选错」。
- **三项阻断/高风险**：
  1. **体积门禁无单一真源**：CI 实际执行 10 MiB（`ci.yml:59`），而产物按文档基线 10,487,296 B 已越线 1,536 B。按当前状态，size gate 将 exit 1、check job 必红。
  2. **容量按「条数」计价**：撤销栈 200 份**全文 `String`**（1MB 文档最坏 200 MiB）；图片纹理缓存 64 张**全尺寸纹理**（单张 12MP 约 46 MiB RGBA）。任意一项都能单独击穿 NFR-PERF-03 的 150 MB 预算。
  3. **性能门禁与 NFR 脱钩**：10KB 解析门禁 50ms 是 NFR 5ms 的 10 倍，增量高亮门禁 40ms 是 NFR 10ms 的 4 倍，1MB 解析门禁 2000ms 是实测 17.7ms 的 113 倍。CI 全绿不能证明 NFR-PERF-05/06 达标：唯一的 16ms 断言（`main.rs:738`）守的是「打字帧」而非「全文高亮」，而 `highlighter_test.rs:478` 明言 syntect 整篇基线约 24ms/7KB、根本达不到 10ms——NFR 实际依赖增量路径，但增量路径的门禁是 40ms。

**明确结论**：作为**产品默认值**，这些数值大体合理；作为**工程门禁**，当前状态不可长期维持。修复 P0（§7.1）后可判定为「基本合理」，修复 P1 后可判定为「合理」。

## 1. 评估方法与证据

判据四条，逐项适用：

| 判据 | 含义 | 不通过的表现 |
|---|---|---|
| A 需求锚定 | 有 FR/NFR 明文或规范依据 | 数字只存在于注释里，需求文档无对应项 |
| B 余量合理 | 阈值 / 实测 ≥ 2 且 ≤ 10；超出需说明用途 | 余量 <1.5（易误报）或 >20（门禁失效） |
| C 失效后果可控 | 击穿后是降级、提示或可恢复错误 | 击穿后崩溃、数据丢失或内存失控 |
| D 单一真源 | 同一语义只有一处定义 | 多处副本可独立漂移 |

**证据来源**：`REQUIREMENTS.md`（FR/NFR 明文）、`docs/metrics.md`（实测基线）、代码注释中的实测数字。**本轮未重新构建或跑基准**，余量按文档记载的实测值计算；文档未记载实测值的项（如 1MB 全文查找）只判定门禁语义，不计算余量——不做推测填充。

余量定义为「门禁阈值 ÷ 文档实测值」，越大表示门禁越松。

## 4. 过松

**S-1 性能门禁普遍只防「数量级退化」，不守 NFR。**
`perf_10kb_parse_p95=50ms` 对 NFR 5ms 是 10 倍；`perf_10kb_incremental_frame_p95=40ms` 对 NFR 10ms 是 4 倍。两者都注明「宽松上限／目标 ≤10ms」，说明是**有意为之**。后果是：解析从 0.17ms 退化到 49ms（仍绿）已违反 NFR 近 10 倍，CI 不会报警。

需要区分两类反例，避免把结论说过头：`main.rs:738` 有 `typing_p95 <= 16.0`、`:729/:743` 有 `idle/after_p95 <= 5.0`，它们确实在守交互帧预算与缓存命中；`highlighter_test.rs:478` 则明确记录「整篇 syntect 高亮约 24ms/7KB，达不到 NFR-PERF-05，阶段 08 靠视口增量达标」。也就是说：**交互帧有 16ms 硬约束，但 NFR-PERF-05/06 的 10ms/5ms 本身没有对应断言**，增量路径只有 40ms 的宽松上限。指标与门禁之间仍是脱钩的，只是没有到「完全无约束」的程度。

**S-2 1MB 三项是「灾难探针」而非性能门禁。**
解析 2000ms（113×）、滚动 200ms（168×）、首屏 500ms（10.4×）。作为「防止 O(N²) 回归」的 tripwire 是合理的，但它们在 CI 摘要里与 NFR 指标并列展示，容易被误读为「性能达标证明」。

**S-3 撤销深度按条数计价。**
`UndoPolicy::default_policy()` 为 200 份，每份 `Snapshot.content: String` 是全文副本（`undo.rs:64-74`，注释已自认「阶段 08 若成热点再改补丁链」）。1MB 文档连续编辑跨越 200 个 400ms 合并窗口（约 80 秒）即达 **200 MiB**，单独超过 NFR-PERF-03 的 150 MB。当前没有任何字节上限。

**S-4 图片缓存按张数计价，且纹理为原始分辨率。**
`IMAGE_CACHE_CAPACITY=64`，`decode()` 直接 `image::load_from_memory` → 全尺寸 `ColorImage` → `load_texture`（`image_cache.rs:311-318, 264-268`）；显示时才缩到 620pt。文件 512KB 的 JPEG 完全可能是 6000×4000，解码后 96 MB。64 张的理论峰值约 2.9 GiB。512KB 文件上限既**挡不住显存**（压缩比不可控），又**过紧地误伤普通照片**——同一个数字同时犯了两个方向的错。

**S-5 预警线低于当前产物。**
CI `SIZE_WARN_BYTES=8388608`（8 MiB）比产物低 2 MiB，预警永久点亮；本地预警线 10 MiB 也比产物低 1,536 B。告警疲劳会让真正的越线被忽略。

## 5. 过紧

**T-1 图片 512KB 全来源硬上限。**
限制写在 `AssetLimits::default()`，对本地文件、远程 URL、data URI 一视同仁。但「内联进 Markdown 文本」才是需要小上限的场景；本地/远程图片没有文本膨胀问题。一部手机照片 2–5MB、截图 300KB–1MB，当前策略会让大量正常图片显示为占位。这是**用户可直接感知的功能缺陷**，不是理论风险。

**T-2 搜索总量 300 命中。**
`search_perf_test.rs:238` 的夹具就是 1000 个文件、每份正文含「文档」；搜索「文档」时会立即触顶 300 并被标记 truncated。仓库自己的性能用例已经证明该上限在「真实规模工作区」下必然触发。叠加「无分页、无加载更多」，用户会得到**静默不完整**的结果。

**T-3 文件树 5000 条。**
`skip_hidden + ignored_dirs` 已过滤 node_modules/target 等，剩余条目在 monorepo 或大文档库中仍可超 5000；超出后树不完整，且没有 truncated 提示（`fs_workspace_repository.rs:60`）。

**T-4 字号/行高档位缺口（偏紧的表现形式）。**
合法区间 8–48 / 1.0–3.0，但 UI 只给 12–20（7 档）/ 1.4–2.0（6 档），并用 `f32::EPSILON` 严格比较。合法但无档位的值在设置页表现为「全不选中」，用户无法判断当前值。这是区间与档位两侧都「紧」的结果。

## 7. 调整建议

### 7.1 P0（阻断级，建议合并前完成）

| # | 动作 | 具体数值/位置 | 预期收益 | 风险 |
|---|---|---|---|---|
| P0-1 | 体积门禁收敛为单一真源 | `ci.yml:59` → `11534336`；`:60` → `11010048`（10.5 MiB）；`package-{linux,macos}.sh`/`package-windows.ps1` → `11534336`；`REQUIREMENTS.md:27,101` → 11 MB | 消除 CI 必红；预警线恢复「可行动窗口」（约 512 KiB） | 若希望保留「10 MiB 旧承诺」语义，需接受永久预警——不建议 |
| P0-2 | 明确门禁对象 | exe 与安装包分别命名（`SIZE_LIMIT_BIN_BYTES` / `SIZE_LIMIT_PKG_BYTES`），不再共用一个数字 | 避免 zip 7.14 MiB 与 exe 10.0 MiB 用同一红线 | 需同步 CI 与三个脚本 |
| P0-3 | 撤销栈加字节预算 | `UndoPolicy` 增 `max_bytes`，建议 **64 MiB**；超限从最旧开始丢弃；过渡期可先把 `max_depth` 200→100 | 1MB 文档撤销内存从最坏 200 MiB 降到 ≤64 MiB | 历史深度变浅；用户可感知「撤销不够远」 |
| P0-4 | 图片按字节计价 + 解码降采样 | 缓存预算 **128 MiB**（按 `texture.size` 估算 W×H×4）；解码前按最长边 **1600px** 降采样 | 显存/内存可预测；普通照片可预览 | 降采样后放大略糊；需改解码路径 |

## 8. 不建议调整的项

以下项经评估取值合理，改动收益低于风险，建议保持：

- **IME 800/50ms**：两个方向相反的保护窗，取值与击键间隔、帧间隔的量级匹配，是本仓库论证最充分的一组。
- **分栏 0.2–0.8、侧栏 180–560、0.6 share、窗口最小 960×600**：只影响布局美观，且有动态兜底。
- **滚动抑制 100ms、消息 TTL 4s**：处于人类感知阈值两侧，改动易引入新的时序缺陷。
- **diff 2M 单元格、快速打开 12 条、拼写 3/1/2/5、表格 100×32**：均有原型对齐或明确的误报/性能取舍。
- **导出 8192/16384/256 段、崩溃报告 10 份、去重 1000 次**：边界明确、失败路径可控。
- **覆盖率 70/90 + 2% 缓冲**：与 NFR 同值，缓冲是防抖而非放宽。
- **`.rustfmt.toml` 100、`deny` 0.93、工具链 1.99**：工具链一致性约束，不属于业务阈值。

## 9. 复评触发条件

出现以下任一情况时应重跑本评估，而不是等年度评审：

1. release 产物达到 **10.5 MiB**（新预警线）——距 11 MiB 红线不足 0.5 MiB。
2. 新增图片解码/缓存路径，或图片上限调整（S-4/P0-4 强耦合）。
3. `max_open_documents` 上限或渲染/高亮缓存容量调整（32/30 已贴线）。
4. NFR 文档修订（尤其 PERF-01/03/04）——所有「需求锚定」判据随之失效。
5. perf job 连续 3 次出现同一用例失败或抖动（说明阈值与 runner 方差失配）。

## 10. 评价结论（一句话版）

**这些阈值作为产品默认值是合理的；作为工程门禁，当前存在 1 项阻断（体积）、2 项计价错误（撤销/图片）和 1 类语义错位（性能门禁不守 NFR）。先修 P0 的四项，体系即可从「不可维持」回到「基本合理」；P1 完成后再收敛为单一真源，才算真正合理。**

## 12. 开发期接入（2026-10-25）

基线不再只是「文档」：它现在有机械消费者，进入编码期门禁。

### 12.1 机制

| 环节 | 实现 | 作用 |
|---|---|---|
| 基线可定位 | 每条增加 `anchor`（源码行必须出现的片段）与 `via`（消费单一真源时指向定义文件） | 允许行号漂移被发现，别名阈值在定义处校验 |
| 校验器 | `tools/check_thresholds.py`（纯标准库，无 PyYAML） | 锚点定位 + 数值表达式求值（`500 * 1024` → 512000）+ 少量枚举映射（`TabSize::Four` → 4） |
| 失败语义 | 数值不符 / 锚点丢失 / 歧义 → exit 1；行号漂移 → WARN | `--strict-lines` 把漂移升级为失败；`--fix` 只回写行号 |
| CI | `check` job 增加 `Threshold baseline`（Linux 单平台） | 改了常量忘改基线即红 |
| 本地约定 | `CONTRIBUTING.md` 验证链 + `.agent/conventions.md` §十 | 编码期上下文显式要求「先改常量、再改基线」 |

### 12.2 变异验证

| 变异 | 期望 | 实测 |
|---|---|---|
| 基线数值改为 999 | exit 1 | `FAIL: artifact_size_limit_ci: 数值不符，期望 999` ✅ |
| 锚点改为不存在 | exit 1 | `FAIL: 锚点丢失` ✅ |
| 行号 +5 | WARN + exit 0 | `[drift] 行号 65 → 60` ✅ |
| 同上 + `--strict-lines` | exit 1 | `FAIL: 行号漂移 1 处` ✅ |
| 同上 + `--fix` | 回写并 exit 0 | `[fix] 回写 1 处行号`，复查通过 ✅ |

### 12.3 顺带修正的基线错误

校验器在首次全量比对时发现：`asset_max_inline_bytes` 的基线值写成 **512000**，而源码是
`512 * 1024 = 524288`。这是此前人工口径（把 512 KB 当成 500 KiB）造成的笔误，已改为
**524288**；说明「机器比对」确实能抓到人眼漏掉的数值错误。

### 12.4 边界

- 校验器**不读取也不修改程序行为**：它只比对源码与 YAML，`runtime_consumed: false` 不变。
- 参数化阈值（`AssetLimits`、`UndoPolicy`）仍以默认值入基线；测试用 `with_*` 构造的局部值不进基线。
- 非数值阈值（版本号、日志级别、档位列表）只校验锚点存在，不做数值比对（已在输出中计为「跳过」）。
