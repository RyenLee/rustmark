## 3. 缺陷 DEF-01：查找器大小写不敏感路径为 O(N×M)

### 现象

1MB 样本上「大小写不敏感」全文查找耗时远超门限，导致集成测试整轮跑了 **351 秒**（其余测试合计约 1 秒）。

### 根因

`src/presentation/state/find_replace_ui_state.rs` 的 `find_literal_ignore_case`：

```rust
let haystack: Vec<(usize, char)> = text.char_indices().collect();  // ← 每次调用重建整篇文档
for index in 0..haystack.len() { /* 逐字符比对 */ }
```

而 `Finder::scan` 的主循环**每找到一个命中就调用它一次**：

```rust
while at <= text.len() && matches.len() < MAX_MATCHES {
    let Some(found) = find_from(&pattern, options, text, at) else { break };
    ...
}
```

于是：构建整篇字符表 O(N) × 命中数 M次 = **O(N×M)**。
`MAX_MATCHES` 上限 10 万，理论上最坏可退化到极慢。

### 实测数据（debug 构建，本机）

| 场景 | 耗时 | 说明 |
|---|---|---|
| 100KB，大小写**敏感**，0 命中 | **84 µs** | 走 `str::find`（memchr），极快 |
| 100KB，大小写**不敏感**，0 命中 | **14.7 ms** | 慢 175 倍 |
| 200KB，不敏感 | 27.5 ms | 线性于 N（0 命中时） |
| 400KB，不敏感 | 57.1 ms | 线性于 N（0 命中时） |
| 8KB / **1,000 命中** | 30.4 ms | — |
| 16KB / **4,000 命中** | **517 ms** | 命中数 ×4 → 耗时 ×17，**确认超线性** |

对照组证明：**1MB 规模本身完全可查找**（大小写敏感仅 0.86ms），瓶颈只在折叠路径的算法，不在数据规模。

### 影响面

- 编辑区查找替换面板（`Ctrl+F`）默认关闭大小写敏感 → 大文档下输入即卡顿。
- 工作区跨文件搜索同样走该路径。
- 与 FR-06「大文件降级」无关：降级只作用于**预览渲染**，查找未做降级。

### 处置

按 `docs/07-集成联调与原型对齐.md` §4 关键约束「**失败不绕过**：本阶段发现的缺陷回到对应阶段任务修复，禁止在本阶段写 UI 层补丁」：

- 本阶段**不修复**，缺陷登记为 **DEF-01**，归属阶段 **S6-08**（查找替换）。
- `large_full_text_find_is_bounded` 标记 `#[ignore]` 挂起（附缺陷原因），修复后恢复为门禁。
- 新增 `large_find_case_sensitive_is_bounded` 作为对照基线，确保「1MB 可查找」这一事实被门禁守住。
- **修复方向建议**（供 S6-08 参考，不在本阶段实施）：把逐字符小写折叠表提到 `Finder::scan` 层构造一次并复用，而非每次 `find_from` 重建；或在 `scan` 内改用单次线性扫描 + 小写映射缓存，使整体回到 O(N)。

## 4. 降级触发验证（FR-06）

阈值：`TRUNCATE_THRESHOLD_BYTES = 500 * 1024 = 512000` 字节（`src/application/markdown/service.rs:38`）。

| 用例 | 断言 | 结果 |
|---|---|---|
| `degrade_triggers_above_threshold` | 1MB > 阈值 → `truncated=true` 且 `blocks` 为空 | ✅ |
| `no_degrade_below_threshold` | 普通文档 → `truncated=false` 且有块 | ✅ |
| `degrade_boundary_is_exactly_at_threshold` | 恰好 512000 字节 → **不降级**（阈值语义是 `>` 而非 `>=`） | ✅ |
| `degrade_avoids_parse_cost_entirely` | 注入一个「被调用即 panic」的解析器 → 仍正常返回，证明降级路径**根本不碰解析器** | ✅ |

最后一条是比计时断言更硬的证明：它验证的是**控制流**而非性能数字。

## 6. 待确认项（需评审决策，未自行假设）

### Q1：非法 UTF-8 的契约——「明确报错」还是「lossy 兜底」？

> **决策状态：已定（选 A）**。用户于 2026-10-08 确认维持 `from_utf8_lossy` 兜底，不改生产代码，仅修正规范措辞。

- **S7-04 规范原文**：「非法 UTF-8 字节（应明确报错而非崩溃）」，验收标准亦写「非法 UTF-8 返回明确错误」。该措辞已按决策更正为「不崩溃且不丢上下文」。
- **现有实现**：`FsDocumentRepository::decode` 用 `String::from_utf8_lossy`，非法字节替换为 `U+FFFD`，代码注释明确写着 rationale：

  > `from_utf8` 失败时用 `from_utf8_lossy` 兜底：编辑器不该因为一个非法字节就打不开文件（替换字符 U+FFFD 是业界通行做法）。

- **结论**：规范与实现原为相反的产品行为，现以**实现为准**——非法 UTF-8 文件**不崩溃、前后文不丢、可正常打开与解析**，非法字节以 `U+FFFD` 呈现。无需改代码；建议后续在状态栏给一次性提示（属增强项，非契约要求）。

| 选项 | 行为 | 影响面 | 决策 |
|---|---|---|---|
| **A. 维持现状**（推荐） | lossy 替换为 `U+FFFD`，状态栏可给一次性提示 | 无需改代码；S7-04 文档措辞已改为「不崩溃且不丢上下文」 | **✅ 已选** |
| B. 改为明确报错 | 拒绝打开并报错 | 需改 `decode` 返回 `Result` 并调整调用方；用户将无法用编辑器打开 GBK 等非 UTF-8 文件 | 未选 |
