**增量归因（2026-10-13 ~ 10-14 两笔，均有问题记录可查）**

| 增量 | 估算体积 | 内容 | 记录 |
|---|---|---|---|

| 其余（甘特图重写、检查/搜索截断修复等代码） | ≈ +0.0~0.1 MiB | 均为小量代码增长 | 问题记录 024 / 025 |

**⚠️ 待决策（不自行处置，理由如下）**：`NFR-PERF-01` 的 10 MB 红线被越过，
但两笔增量都是**用户明确要求的功能**（「内置字体，下拉不再取决于本机装了什么」
「https 图片要能显示」），回退任何一笔都等于撤功能。可选缓解方案（供评审）：

1. **字体改为「首次使用时解包到用户数据目录」或安装器外置资源**：主程序立减
   ≈2.4 MiB 回到 8.6 MiB（预警线之上、红线之下）；代价是「开箱即用」变两步。
2. **CJK 子集从 GB2312 缩到常用 3500 字**：资产 1.57MB → 约 0.8MB；生僻字在
   无系统中文字体的环境下变方框（与内置初衷相悖，不推荐单做）。
3. **TLS 换 `native-tls`（Windows=schannel / macOS=Security.framework）**：
   预计省 ≈1 MiB（ring + webpki 不进二进制）；代价是 Linux 链 OpenSSL（交叉
   编译困难）且三平台行为不再一致。
4. **维持现状**：11.04 MiB 对桌面编辑器仍是轻量级（vs 典型 Electron 100 MiB+），
   红线数字本身来自 v1.0 需求基线，可在 v1.1 评审中修订。

在决策落地前，`NFR-PERF-01` 视为**已知超限、带豁免候选**，不做静默处置。
**后续**：方案 1 于 2026-10-19 / 10-22 分两步落地（三款内置字体 + egui 默认字体），
方案 3 以「保留 rustls、根证书运行期读取」的等效形式落地，最终数字见 §2.7。

- 方案 1（字体外置）：已由 T2 完成「内置三款 + CJK + 数学」的外置，本次把 **egui 默认字体**

- 方案 3（TLS 换 `native-tls`）：**否决**。Linux 端要链 OpenSSL，在 Ubuntu 22.04 构建链

- `ureq` 的 `platform-verifier` 方案也被否：该 crate 会引入 `windows` / `objc2` 大件，

- 余量仅 18,944 B（0.18%）。任何后续功能增量都会先吃掉它，CI 的体积门禁随时可能转红。

- **macOS / Linux 产物未在本机复测**：字体外置与根证书外置对三者都成立，但 Linux 侧另有
  `x11` / `wayland` / `rfd` 的 GTK 依赖，实际字节数须在 CI 或真机上重测后才可对三平台下结论
  （见差距报告 DOC-02 待办）。

### 3.0.2 内存归因：**本项目自身的内存贡献 ≈ 0.9 MB**

用「地板探针」把图形栈基线与自有代码分开（测完即删，沿用 §3.1 先例）：
一个**空的 eframe + wgpu 窗口**（不引用 rustmark 任何模块，故 syntect / ropey /
pulldown-cmark 均不参与链接）与完整应用对比：

| 被测对象 | Private Working Set | WorkingSet64 |
|---|---|---|
| 完整应用 `rustmark` | 125.3 MB | 189.4 MB |
| 空 eframe+wgpu 窗口（地板） | 124.4 MB | 186.8 MB |
| **差值（= 本项目全部自有代码 + 全部依赖数据）** | **≈ 0.9 MB** | ≈ 2.6 MB |

**结论**：

1. 空闲内存 ~125 MB（private）几乎**全部是 egui + wgpu + dx12 的固有基线**，
   本项目自身（含 syntect 语法集常驻、ropey、解析器、各类缓存）只贡献 **约 0.9 MB**。
2. 因此 **S8-04 的 §8.3 五项（Rope 唯一缓冲 / LayoutJob LRU 64 / Galley 缓存 /
   纹理缓存 / 撤销栈上限）在本口径下没有可观测的优化空间**——即便把它们全做到极致，
   能省的也是这 0.9 MB 里的一部分。
3. **原 ≤100 MB 阈值与实测基线在数学上冲突**：在 wgpu 后端（ADR-001 锁定）下，
   光是空窗口就要 ~125 MB。**这不是实现缺陷，是需求假设与实测的冲突**——
   已上报需求方，裁定结果为 **ADR-006：阈值改为按平台各自口径，Windows ≤ 150 MB
   （判定口径改为 Private Working Set）**，实测 125.3 MB ✅ 达标
   （见 `docs/adr/ADR-006-memory-threshold-revision.md` 与
   `docs/archive/stage-reports/optimization-log.md` OPT-007）。
4. 判定口径改为 Private Working Set 的实测依据：完整应用的 WorkingSet 甚至
   **略低于**空窗口探针（189.2 vs 210.1 MB，另一次 189.4 vs 186.8 MB）——
   说明 WorkingSet 受 OS 换页与共享页影响，噪声可达 ±20 MB，
   **不适合用来判断 1 MB 量级的优化收益**。归因与判定一律以 **Private Working Set** 为准。

> 三口径不可横向比较（Windows Private WS / macOS footprint / Linux VmRSS），
> 门禁按「各平台各自阈值」判定；macOS 与 Linux 本机无法实测，转 Stage 09 真机补测，
> 且**补测时同样先做地板探针**再定阈值（ADR-006 待办）。

#### 3.2.1 编辑帧成本归因（`measure_markdown_highlight_parse_vs_classify`）

把一次 10KB Markdown 全量高亮拆成两段，判断成本到底在哪：

| 段 | 实测（release, p50） | 占比 |
|---|---|---|
| **syntect 逐行解析**（`ParseState::parse_line` + 区间迭代） | **58.38 ms** | **97.4%** |
| 其余（scope 栈 → `SpanStyle` 判定 + 片段合并 + `Vec` 增长） | ≈ **1.56 ms** | 2.6% |
| 合计（全量 `highlight`） | **59.94 ms** | 100% |

**结论**：成本几乎**全部**在 syntect 的解析本身，不在本项目的判定与组装逻辑。
这直接否决了一条原本看来最省事的候选（「给 scope → 样式加一张备忘表」）：
即便把判定做成零成本，也只省 2.6%，编辑帧仍会在 58 ms 量级。
OPT-011 已选 **① 防抖降级**（打字期返回空片段、停手后一次性全量高亮）；
② 增量高亮（扩领域 `SyntaxHighlighter` 接口）与 ③ 接受并下调指标均未采用——
前者属架构调整、后者放弃帧预算，均不在本阶段可自决范围。

#### 3.2.2 编辑区每帧成本归因（问题 046）

编辑区（`TextEdit`）是唯一「每帧都跑」的重路径。§3.2.1 回答的是「真要重算时贵在哪」，
本节回答的是另一半：**文档没变的那一帧，我们自己还花了多少**。
这也是对照 `docs/logs/T.txt`（egui `TextEdit` 大文本卡顿分析）做审计时的量化依据。

```text
cargo test --release --test presentation -- --nocapture textedit_frame
```

口径同 §3.2：release、预热两帧后取 30 帧、p50 代表典型体验（样本 30 个时 p95 即最大值，
故断言只用 p50）。语料为中文 Markdown（含标题 / 列表 / 引用 / 代码块），
经真实 `EditorApp` + `main_view::show` 驱动（关预览与侧栏，隔离编辑区）。

| 档位 | 修复前 p50 / p95 | 修复后 p50 / p95 |
|---|---|---|
| 10KB（573 行） | 0.14 / 3.64 ms | **0.11 / 0.88 ms** |
| 100KB（5,721 行） | 0.56 / 3.80 ms | **0.33 / 0.81 ms** |
| 1MB（58,514 行，降级纯文本） | 4.44 / 8.33 ms | **3.16 / 4.06 ms** |

> **2026-10-16 复测（问题 047 编辑区几何改动后）**：10KB **0.12 / 0.80**、
> 100KB **0.35 / 0.94**、1MB **3.25 / 4.34** ms（p50 / p95），与上表同档无实质差异
> ——该改动只调 `TextEdit` 的最小高度与滚动区 `auto_shrink`，不改变排版量。

**每帧前置工作分项（100KB，5,721 行，3,080 个 span）**

| 项 | 修复前 p50 | 修复后 p50 | 处置 |
|---|---|---|---|
| 高亮查询（缓存命中） | 0.108 ms | **0.000 ms** | 见结论 1、2 |
| 行数扫描 | 0.048 ms | 0.029 ms | `split('\n')` → 字节扫描 |
| 光标行号换算 | 0.102 ms | 0.027 ms | `chars()` → 字节扫描；关行号栏时不再计算 |
| 旧文本克隆 | 0.002 ms | 0.002 ms | **实测证否，未改**（见结论 4） |

**结论与处置**

1. **主因是「为两个整数付 O(全文)」**。`highlight` / `spell_check` 每帧先调
   `content_and_revision` → `Document::text()`，把整篇文本从 rope 快照成一个新
   `String`；而这一帧真正需要的只有**版本号**（防抖计时 + 缓存键）与**字节长度**
   （大文件降级），两者都是 O(1)。改用新增的
   `DocumentContentProvider::revision_and_len` 后，缓存命中 / 防抖期 / 大文件降级
   三条路径**一次都不再快照全文**——1MB 文档每帧省下一次 MB 级分配 + 拷贝。
   与问题 043（预览区只取版本号）同一根因，当时只覆盖了预览。
2. **高亮结果改为共享快照** `Arc<Vec<SpanView>>`。100KB 文档 3,080 个 span，
   按值返回等于每帧克隆 3,080 个 `String`（每段都带 `style` 串）——共享后该项
   降到计时器分辨率以下（<0.001ms），且随文档线性增长的那部分彻底消失。
3. **行数 / 行号一律按字节数换行**，规则收敛到 `shared::text::{line_count, line_index_at}`。
   依据是 UTF-8 的性质（`\n` = 0x0A，续字节恒 ≥ 0x80 → 字节计数 ≡ 字符计数）；
   release 下行数扫描 **1.65×**、光标行号换算 **3.8×** 提速。
   原先四处各写一份 `split('\n').count()`，现由同一个函数供编辑区 / 行号栏 / 状态栏 / 统计。
   ⚠ **该优化只在 release 下成立**：debug 下字节形式反而更慢
   （100KB 行数 0.093ms vs 0.266ms，迭代器与闭包未展开）。数字一律以 release 为准。
4. **旧文本克隆 0.002ms —— 实测证否，不动**。`prev = editor_text.clone()` 每帧执行
   看着像浪费，实测 100KB 仅 0.002ms（1MB 约 0.02ms）；要消掉它必须换掉 diff 的
   旧文本来源（改动正确性风险高于收益）。
5. **p95 的改善本身就是收益**。修复前 p95 3.6–8.3ms 而 p50 仅 0.14–4.4ms，
   毛刺来自每帧那次大块分配；现在 10/100KB 的 p95 不足 1ms。
   「平均帧够快但偶发卡一下」正是用户能感知的那种卡顿。
6. **剩余成本（1MB 约 3.16ms）不在本项目**。>500KB 已走降级（不着色），
   这 3ms 全部来自 egui 对 58,514 行 `Galley` 的逐行处理与栅格化。
   `docs/logs/T.txt` 的**方案一（视口虚拟化）**正是针对这一项，但 0.37 的
   `TextEdit` **不提供**该能力（无 `show_viewport` / `visible_range`），要它只能自绘
   编辑器——不在本期范围。逐条审计见 `docs/archive/stage-reports/textedit-lag-audit.md`。

   > ⚠ **2026-10-16 问题 049 限定**：本条测的是**空闲帧**（3.16ms），其归因仍成立；
   > 但由此推出的「1MB 要达标只能自绘编辑器」**不成立**——击键帧的大头不在这 3ms 里，
   > 见 §3.2.4 与 `docs/archive/stage-reports/textedit-cost-attribution.md`。

**守卫**：`tests/presentation/textedit_frame_perf_test.rs` 对三档空闲帧 p50 断言
（release 8 / 8 / 24 ms，debug ×8），只钉「数量级退化」（例如有人再把全文快照拖回帧路径），
不做数字裁定。「每帧不得快照全文」另有**确定性**钉法——按调用计数断言，见
`tests/application/markdown_service_test.rs::highlight_frame_path_never_snapshots_the_whole_document`。

#### 3.2.3 编辑区击键帧成本 —— `NFR-PERF-04`「连续输入 100 次」实测（问题 048）

§3.2.2 量的是「文档没变的那一帧」，本节补上指标的原口径：**连续输入 100 次、取 p95**。
此前这一档只有「空闲帧已实测、击键帧待阶段 09」的挂账，现已闭合。

```text
cargo test --release --test presentation -- --nocapture measure_textedit_typing
```

口径：注入**真实的** `Event::Text`（走 egui 文本输入 → `TextEdit` 改写文本 → 应用侧
diff / 排版 → 重绘，而非直接改 `editor_text`），每帧显式推进 8ms——约 125fps 的连续
人手节奏，间隔 < 150ms 防抖窗。装配用**可控时钟**，故「全程在防抖窗内」是确定状态，
不依赖机器快慢（真实 `SystemClock` 下用例会随时钟漂移而改变被测行为）。

| 档位 | 击键帧 p50 / p95（release） | 同运行空闲帧 p50（5 帧） | 16ms 预算 |
|---|---|---|---|
| 10KB（573 行） | **0.44 / 0.58 ms** | 0.15 ms | ✅ 余量 27× |
| 100KB（5,721 行） | **3.34 / 4.01 ms** | 0.62 ms | ✅ 余量 4× |
| 1MB（58,514 行，降级纯文本） | **39.21 / 42.00 ms** | 7.27 ms | ❌ **超 2.6×** |

> 同运行空闲帧只有 5 帧样本（p50 取第 3 个），比 §3.2.2 的 30 帧基线偏高；
> 1MB 的对照口径以 §3.2.2 的 **3.25ms** 为准。

**结论**

1. **≤ 100KB 达标且余量充足。**击键帧 = 空闲帧 + 「文本变更」引发的增量重排：
   10KB 只贵 0.29ms、100KB 贵 2.7ms，都是「只重建改动那一行」的量级，与 §3.2.2
   的增量设计（重建行数 == 1）一致。
2. **打字期一次全量高亮都没有发生——用计数证明，不用耗时推断。**
   100 次输入期间高亮缓存 `misses` 增量为 **0**（三档一致）；对照实验（停手越过
   150ms 窗口）让它**涨 1**。变异验证：把防抖短路注掉后，同一条断言立刻抓到
   **99 次**解析。⇒ OPT-011 ①「打字期不上色」在连续输入下确实生效。
3. **1MB 档超指标，根因在应用层——不在 egui、也不在排版层。**
   本节原文把根因判给「egui 文本一变即重建 58,514 行 `Galley`，这笔成本无法在本项目内
   规避，只能自绘编辑器」，该判定**已被问题 049 的实测证伪**（§3.2.4）：
   100 帧连续击键里**每帧真正重排的行数最大值为 1**，整篇重排从未发生；
   40.92ms 的真实构成是「空闲帧 7.06 + 排版层 9.24 + `diff_replace` 6.93 + 余下 17.68」，
   其中 `E1 − E7 = 23.67ms` 全部来自 `EditorApp` 的文本变更链（裸宿主里没有这些）。
   用自绘编辑器替换编辑表面**动不到这 23.67ms**，故「只能自绘」的推论一并撤回。
   **据此不假装 1MB 达标**，只对 10KB / 100KB 守 16ms 指标。

   > ⚠ **2026-10-16 问题 049 改写**：本条的原始表述为「文本一变就要重建 58,514 行的
   > `Galley`，42.00ms 与空闲帧 3.25ms 的差（约 39ms）来自这里……只能自绘编辑器」。
   > 证伪依据与本条的关系见 §3.2.4 结论 1；完整报告见
   > `docs/archive/stage-reports/textedit-cost-attribution.md`。
4. **1MB 的 `misses` 同样不增**（> 500KB 走降级路径，压根不进高亮器），
   所以第 2 条的计数断言在三档上一致成立——它钉的是「打字期不得解析」，
   与档位是否降级无关。

**守卫**：`textedit_frame_perf_test.rs::measure_textedit_typing_frame_at_three_sizes`
对 ≤ 500KB 断言 p95 ≤ 16ms（指标本身），对 1MB 给 64ms（语义退化为「防数量级退化」）；
三档都断言「打字期 `misses` 不涨」。
`typing_cheap_because_highlight_is_deferred_not_absent` 提供对照，并钉住「停手后防抖
已追上文档版本」（`highlight_pace_snapshot`）。

#### 3.2.4 编辑区 1MB 击键帧成本归因（问题 049）

§3.2.3 只记录了 1MB「超指标」的数字与一个**根因判定**。本节用八组对照把 40.92ms
拆开，并据此**撤回**该判定（原文「egui 文本一变即重建 58,514 行 `Galley` ⟹ 只能自绘编辑器」）。

```text
cargo test --release --test presentation -- --nocapture profile_1mb_typing_frame
```

口径同 §3.2.3（真实 `Event::Text`、每帧推进 8ms、可控时钟）。E3 与 E7 **共用同一个
探针函数**，唯一差别是是否挂自定义 layouter，故 `E7 − E3` 干净地隔离出「自家逐行排版
相对上游按段落排版的净开销」；`E1 − E7` 则隔离出「`EditorApp` 的每帧前置工作 +
文本变更回写链」（裸宿主里没有这些）。

| 组 | 被测对象 | p50 | p95 |
|---|---|---|---|
| E1 | **现状**：真实 `EditorApp` + 逐行 layouter | **40.92** | 43.42 |
| — | E1 同运行空闲帧 | 7.06 | — |
| E1 | 每帧真正重排的行数（100 帧） | **max = 1** | — |
| E2 | 排版层·文本变一字节（`highlight_layout_with_find`） | 9.24 | 11.17 |
| E2b | 排版层·整文档缓存命中 | **0.238** | — |
| E3 | 裸 `TextEdit` + 上游默认 layouter（按段落缓存） | 19.04 | 20.40 |
| E7 | 裸 `TextEdit` + 本项目逐行 layouter | **17.24** | 17.88 |
| E8 | `editor_ops::diff_replace`（1MB 整篇） | 6.93 | — |

```text
40.92 = 空闲帧 7.06 + 文本变更 33.86
33.86 = 排版层 9.24 + diff_replace 6.93 + 余下 17.68
应用层净开销（E1 − E7） = 23.67   ←── 占击键帧 58%
```

**结论**

1. **「文本一变即重建 58,514 行 `Galley`」证伪。** 100 帧连续击键里每帧重建行数
   **max = 1**，E2 的 20 次独立调用取值集合为 `{1}`——逐行增量缓存（`LINE_LAYOUT` +
   内容差分映射）完全正常，整篇重排从未发生。§3.2.3 结论 1（重建行数 == 1）才对。
2. **自研逐行排版层不慢于上游。** 同一宿主、同一文本、只换 layouter：E7 **17.24** <
   E3 **19.04**（三轮运行方向一致，差额 1.80~4.10ms）。⇒ 自研排版层是有效资产；
   「换成上游默认 layouter」不是出路。
3. **大头在应用层，其中一处是确定性缺陷。** `E1 − E7 = 23.67ms` 全部来自 `EditorApp`
   的文本变更链；`editor_ops::diff_replace` 单项 **6.93ms**——它把 1MB 文本两侧各
   `chars().collect::<Vec<char>>()`（约 2×1.4MB 分配 + 两遍 UTF-8 解码），再调两次
   `char_to_byte`（内部 `char_indices().nth(k)`，O(k)）。与问题 046「为两个整数付
   O(全文)」同一性质，属**低风险可优化项**（改字节层前后缀比较即可）。
4. **1MB 达标不需要自绘编辑器。** 自绘替换的是编辑表面与排版，动不到第 3 条的
   23.67ms；而排版层已证明不劣于上游。原判定链「egui 无虚拟化 ⟹ 只能自绘」作废，
   「是否自绘」应作为独立议题（收益面只剩超大文档可编辑性）重新评估。

**遗留**：余下 17.68ms 未拆开，嫌疑清单与后续步骤见报告 §5。

**守卫**：`tests/presentation/textedit_cost_attribution_test.rs::profile_1mb_typing_frame_cost_attribution`
按**计数**断言「每帧重建行数 ≤ 4」（实测恒为 1），钉住「逐行增量不得退化成整篇重排」——

2. **关掉状态栏仍 30.43ms（超标 1.9×）⇒ 单修一项不够**，但剩余三项分别在应用层、

> ⚠ **③ 已于第三轮落地**（§3.2.6）：实测 6.93 → 0.24ms，1MB 击键帧 40.92 → 33.73~34.55。

#### 3.2.6 优化落地：`diff_replace` 字节层前后缀（问题 049 修复）

§3.2.4 / §3.2.5 两轮把 1MB 击键帧拆开后，**唯一的确定性缺陷**是
`editor_ops::diff_replace`（`transform.rs`）：它挂在「每击键一次」的路径上，
却先把两整篇文本 `chars().collect::<Vec<char>>()`（1MB = 2 × 35 万 char，
约 2.8MB 分配 + 两遍 UTF-8 解码），再用两次 `char_to_byte`
（`char_indices().nth(k)`，O(k)）把字符索引换回字节——只为求一个公共前后缀。

**改法**：前后缀改在**字节层**比较（不分配、不解码），再把字节边界用
`str::is_char_boundary` 回退/收拢到字符边界。UTF-8 是自同步编码——某位置是否为
字符边界只取决于该位置自身是否为续字节，而公共前缀段两侧逐字节相同，故边界判定
两侧一致，无需构造任何字符级缓冲。字符索引此时只需**算一次**（`byte_to_char`
于前缀处），光标用「前缀字符数 + 插入内容字符数」推出。

| 量 | 修复前 | 修复后（三轮） |
|---|---|---|
| `diff_replace`（1MB，文末追加 = 前缀最长） | **6.93** | **0.24 / 0.25 / 0.24** |
| `diff_replace`（1MB，文档中点替换） | 6.9（同量级，旧实现与位置无关） | **0.33** |
| 1MB 击键帧 p50（E1） | 40.43 / 40.62 / 40.92 | **34.55 / 33.73 / 35.48** |
| 1MB 击键帧 p95 | 43.42 | **37.41 / 36.12 / 38.56** |
| 1MB 同运行空闲帧 | 7.06 | 7.32~7.65 |

改后三轮 E1 区间（33.7~35.5）与改前（40.4~40.9）**无重叠**，差额 5.4~6.4ms，与该项
绝对降幅（6.7ms）同量级，交叉印证。

**结论**

1. **单次调用提速约 27×**（6.93 → 0.24ms），击键帧同步下降 6.4~7.2ms；差额与
   `diff_replace` 的绝对降幅一致，说明这笔钱确实全部来自那一处。
2. **成本不再与改动位置强相关**（文末 0.24 / 中点 0.33）——旧实现无论改哪里都要
   整篇字符化，新实现只在前缀处做一次字符计数，量级恒定。
3. **对外语义零变化**：以旧实现为基准做了等价性对照（`diff_replace_matches_char_level_reference`，
   覆盖中文 / 4 字节字符 / 公共前后缀落在字符中间的边界），逐字段相等。
4. 1MB 仍超 16ms 2.3×，**剩余大头是状态栏整篇统计（9.30ms）+ 排版层（9.09ms）
   + 空闲帧（7.5ms）**——即 §3.2.5 的 ①② 两项待办。

**守卫**：`diff_replace` 三条边界单测（前缀回退 / 后缀收拢 / 逐字段等价于旧实现）
+ 归因用例里的量级断言（两位置均须 < 2ms，退化即红）。
变异验证：去掉两处 `is_char_boundary` 调整 → 三条单测立即全部 panic 在非字符边界切片上。

### 3.2.7 排版层缓存 miss 路径去重复分配（问题 052，2026-10-16）

**改动**（`mapper/highlight_layout.rs`、`mapper/highlight_cache.rs`；全部是内部实现，

**守卫**（`tests/presentation/highlight_layout_test.rs`，新增 3 条）

1. `unchanged_lines_share_rows_with_previous_frame`——改一行后，未变的行必须与上一帧
   **共享同一个 `Arc<Row>`**（`Galley::concat` 对每行做 `Arc::clone`，故「复用」≡
   「行的 `Arc` 身份不变」），被编辑的那行必须**不**共享。**结构性断言，不受 CI 抖动影响。**
2. `incremental_reuse_stays_equivalent_to_whole_document_layout`——复用路径的输出必须与

   这里覆盖 5 种编辑形态（等长改字 ×3、插入一行、删除一行）。
3. `whole_document_cache_distinguishes_equal_length_texts`——等长异内容不得互相命中，
   钉住 ① 换掉的只是**存储方式**、不是判据本身。

顺带把 `assert_rows_equivalent` 由「比字形**个数**」强化为「比字形**字符**」：
`'d'` 与 `'1'` 都是 1 个字形，只比个数会让「复用了内容已变的旧行」溜过去。

### 3.2.8 零散每帧成本收敛（问题 053，2026-10-17）

**背景**：§3.2.5 的隔离微基准把「每帧前置工作」拆出 6 项（S1 旧文本克隆 / S2 高亮查询 /
S3 行起点表 / S4 行数 / S5 光标行号 / S6 字数统计）。其中 S3+S4 在 1MB 上合计 **1.1ms/帧**，
且被状态栏（光标的行列、选区行列、「N 行」）与编辑区（`desired_rows`、行号栏宽度）**各扫一遍**
——同一份信息每帧被重复扫描 4~5 次。本项把这几处零碎成本收敛，单条都不大、合起来占编辑区
稳态帧的可见比例。

**改动**（`scroll_sync.rs`、`app/frame.rs`、`app/frame/editor.rs`、`status_bar_view.rs`、
`editor_view.rs`、`domain/document/undo.rs`、`domain/document/aggregate.rs`、
`application/preferences/service.rs`）：

| # | 改动 | 早先的写法 | 性质 |
|---|---|---|---|
| ① | 新增 `LineIndex`：**一遍扫描**同时给出「行起点表 + 行数」；`EditorApp` 每帧按 `(doc, revision, len)` 缓存一份，帧内其余调用 O(1) 复用 | `line_start_offsets` 与 `line_count` 各扫一遍、每处各扫一遍（4~5 遍/帧） | 落地 |
| ② | `sync_goal` 先问 `has_writing_goal()`，**未设目标时跳过整篇字数统计** | 无条件先取 `current_stats()`（一次整篇六遍遍历，miss 时 1MB 上 9.49ms），再把算不出的目标投影丢弃 | 落地 |
| ③ | `UndoStack` 新增 `would_merge`/`merge`；`Document::apply` 先判「会不会合并」再决定**是否构造整篇快照**，合并命中只滚动时间窗（零分配） | `push` 每次都先 `snapshot_at`（含一份整篇 `String` 复制），合并命中再丢弃——连续打字每键白付一次全文复制 | 落地 |
| ④ | `prev = editor_text.clone()` | 每帧无条件克隆 1MB 旧文本（`diff_replace` 的基准） | **据实保留**（见下） |

**④ 为什么保留克隆（而非门控）**：§3.2 的归因里假设「无输入事件文本就不会变」，但同一文件里
有两条**与 `InputState::events` 无关**的写入路径——无障碍 `SetValue`（`accesskit_set_text_request`）
与拖放文本插入（读 `raw.dropped_files`）。按事件判空会**静默丢掉**这两类编辑（辅助技术用户 +
拖放粘贴），而补一条「旧文本退回领域内容」的兜底要么不触发（优化收益为零）、要么触发时正是要省掉
的那次全文复制——两边都不划算。故保留克隆，结论记入 §14.3.2。

**派生收益（非本轮 A/B，依 §3.2.5 实测外推，免环境漂移争议）**

- ① 把 4~5 遍/帧 降为 1 遍 + O(1) 复用：1MB 上省 **~0.8~1.1ms/帧**（S3 0.82 + S4 0.28 各多扫 3~4 次）。
- ③ 连续打字时每个键都在合并窗内：1MB 上每个键省一次 ~1ms 的整篇 `String` 复制。
- ② 默认（未设目标）每帧省一次 `current_stats()` 查表；注意这只堵了「目标进度」支路，
  **状态栏每击键一次的整篇字数统计已纳入防抖（建议一 / 问题 054 落地）**：打字期沿用上次静止值、停手满 150ms 才刷新，每击键省一次 `compute_stats` ~9.5ms（详见 §3.2.9）；**`compute_stats` 六遍遍历合并为 1~2 遍（建议三 / V11-39 ②）已于 §3.2.10 / 问题 055 落地（1MB 单次结算 9.49 → 5.55ms，−42%）**。

### 3.2.9 状态栏字数统计防抖（问题 054，2026-10-17）

**背景**：§3.2.5 把状态栏每击键一次的整篇字数统计点名为 1MB 击键帧的**最大单块**（~9.5ms / 占 23%）。050 的 A2 消融已确认：状态栏每帧查两次 `get_stats`，缓存键含 `revision` → 击键帧 `revision` 必变 → 每敲一个键就把 1MB 全文重新统计。`compute_stats`（`service/stats.rs`）在 1MB 上做**约六遍全文遍历**（按行 `split` + 字节扫链接 + 逐字符扫字数 + `chars().count()` + `chars().filter(!ws).count()` + `line_count`）。用户口径：**打字期显示「上一次静止时算出的字数」、停手满窗口后再刷新**（与 048 `HighlightPace` / 预览防抖同源先例）。**on-demand 统计浮层（点击时刻）必须保持即时、不走防抖**——那是用户主动请求当前精确值。

### 3.2.10 `compute_stats` 六遍遍历合并为 1~2 遍（问题 055，2026-10-17）

**背景**：050 的 A2 消融已确认状态栏每击键一次的整篇字数统计是 1MB 击键帧最大单块（~9.5ms），根因是 `compute_stats`（`service/stats.rs`）在 1MB 上做**约六遍全文遍历**：按行 `split` + 每行 `trim`/判定、`count_links_and_images` 逐字节、`count_words` 逐字符、`chars().count()`、`chars().filter(!ws).count()`、`line_count` 逐字节再扫一次。建议一（§3.2.9）已把这笔成本从每击键热路径移出（防抖到停手帧），但**停手帧仍要付一次 ~9.5ms**——建议三（V11-39 ②）的目标是把六遍遍历合并为 1~2 遍，压低这次结算的单次成本（估 ~4~6ms）。

#### 3.2.11 增量高亮接线：停手帧 59 ms → 0.86 ms（OPT-011 复议，2026-10-19）

OPT-011 当年在「② 扩领域接口做增量」与「① 防抖降级」之间选了 ①，理由是
「增量要么把 syntect 的 `ParseState` 泄漏进领域接口，要么让基础设施层持有
可变状态」。2026-10-19 的 PoC 换了个切法：**领域侧只暴露
`HighlightSession::advance(text, lang)`**（一个纯语义方法，参数是文本和语言，
返回值是 `Vec<SyntaxSpan>`），`ParseState` / `ScopeStack` 全部留在
infrastructure 内部。约束被绕开，遂重新评估并接线。

**机制**

- `SyntectSession` 每 25 行存一个 `(ParseState, ScopeStack)` 检查点；
- **变更区间由会话自己求**（公共前缀 + 公共后缀）：上层不必存第二份全文，
  也不存在「传错区间导致高亮与文本静默不符」的可能；
- 从变更点前最近的检查点恢复，逐行续解；在旧检查点处用 `Eq` 判定收敛，
  收敛点之后的片段整体平移复用；
- 收敛点按**字节偏移**映射回旧检查点（不是行号相位）——插删整行会让行号
  永久错位，按相位判将一次都命中不了；
- 任何前提不满足（前缀被改、语言切换、超 512 KB）→ **静默退化为全量**。

**实测（release，同机 A/B）**

| 场景 | 改动前 | 改动后 | 说明 |
|---|---|---|---|
| 16KB 全文高亮（改 1 行） | 38.62 ms | **1.66 ms（23.2×）** | 30 轮中位；重解 25/590 行 |
| 10KB 编辑区**停手帧**（UI 整帧） | ~59 ms | **0.86 ms** | `typing_cheap_because_highlight_is_deferred_not_absent` |
| 10KB **击键帧** p50 | 0.308 ms | 0.308 ms | 防抖保留，两者正交 |
| `NFR-PERF-05`（10KB ≤ 10 ms） | ❌ 超 5.6×（56.5 ms） | ✅ **0.86 ms（11.6× 余量）** | 56.5 ms 是全量解析的历史基线 |

**防抖保留，不是替代**：增量把「停手后那一次」从 59 ms 压到 1 ms 级；防抖
解决的是「每击键都付一次」。两者叠加才有上表结果。若后续要恢复「打字期也
上色」，增量已把该成本降到可进帧（1.66 ms / 16KB），那是独立的观感决策。

**正确性守卫**

1. `incremental.rs` 单测 7 条：首帧 / 等长替换 / 插入整行 / 删除整行 /
   块注释内插 `*/` 打破跨行状态 / 12 步混合编辑序列 / 前缀篡改退化 / 换语言，
   全部与 `SyntectHighlighter::highlight`（生产实现）**逐片段对拍**。
2. `highlight_reuses_incremental_session_across_revisions`（服务层）钉接线：
   首次由会话完成全量（不重复解析）、跨版本复用同一会话、清缓存时释放会话。
3. 收益基准（`#[ignore]`，release 口径）：
   `cargo test --release --lib incremental::tests::bench -- --ignored --nocapture`。

**已知边界**：撤销/重做会产生「变更点在缓存之前」的编辑，被前缀校验
拦下后退化为全量（正确但慢）；100–500 KB 的检查点内存与 `memcmp` 成本
未实测（该量级仍远低于 500 KB 截断阈值，但属未验证区）。

##### 3.2.12.3 唯一还有量级空间的一块：排版层每帧 `O(全文 + 行数)`

E2 的 4.74 ms 里只有 **1 行**是真正重排的，其余全是「不管改哪都要重做一遍」的
固定动作：

| 动作 | 规模 | 说明 |
|---|---|---|
| `text.split('\n')` | 1 遍全文扫描 + 58k 次 push | 已按上一版行数预置容量（052） |
| `reuse_map` 前后缀比对 | 58k 次行比较 | 行短，单次便宜，但次数是 `O(行数)` |
| 逐行取 `Arc<Galley>` | **58k 次原子自增** | 复用行的 `Arc` 克隆 |
| `job.append(text, …)` | **整篇 1MB 拷贝** | 同时充当整文档缓存键与选区依据，不能省 |
| `Galley::concat(58k)` | 58k 行搬运 + 汇总 | 返回全新整篇 `Galley` |

`egui::TextEdit` 的契约是「你给我一个整篇 `Galley`」，所以**只要还在用
`TextEdit`，这 4.74 ms 里的 `O(行数)` 部分就每帧必付**。把它压到 O(1) 需要
「同高行内编辑只替换那一行、不 re-concat」，即绕过 `TextEdit` 的 galley 契约
——那已经是半自绘的量级，属于 T5 的决策范围，不在本节实施。

**本节不做的事**：不做任何优化，只归因。T5 的选项与推荐见
`.workbuddy/output/优化任务清单.md` 的 T5 条目。

#### 3.2.13 排版层单行编辑原地补丁（A1-4，T5 选型落地，2026-10-19）

**背景**：§3.2.12.3 指出排版层 4.74 ms 里只有 1 行真正重排，其余全是
`O(全文 + 行数)` 的固定动作。T5 当时给了三个选项（自绘只读 / 修订口径 /
压排版层）。本节落地**第三条**——它不是「绕过 `TextEdit` 的 galley 契约」，
而是**复用上一版的整篇 `Galley`，只替换变更行那一片 `rows`**。

##### 3.2.13.1 做法

`highlight_layout_with_find` 在整篇缓存 miss 之后先试快路径
（`try_patch_single_line`）：

1. 用 **`u64` 分组比较**求新旧文本的公共前后缀（1MB ≈ 0.1 ms），
   两端吸附到字符边界；
2. 前置条件全部成立才动手：变更区内**没有换行**（行数/行号不变）、
   变更行的**视觉行数与行高都不变**（否则后续行 y 偏移要整体平移）、
   `row_starts` 与整篇 `rows` 长度自洽；
3. 只重排那一行，把它在 `rows` 里的切片换掉，增量修正
   `num_vertices` / `num_indices`，按「最宽行 × 总高」重建 `rect`，
   `mesh_bounds` 取并集（只用于剔除，偏大安全）；
4. `job.text` 用 `replace_range` **就地改那一段**（独占时），
   不重建整份 1MB 字符串。

任一前置条件不成立 → 原样退回「拆行 + 差分 + 逐行遍历 + `concat`」，
**正确性不依赖快路径是否命中**。

##### 3.2.13.2 排版层分段成本（1MB，单行编辑，30 轮中位）

先用临时探针把 4.08 ms 拆开（探针测完已删）：

| 阶段 | 改前 | 改后 |
|---|---|---|
| 取上一版 + 拆行 | 0.518 ms | — |
| span 准备 + 差分表 | 0.608 ms | — |
| 逐行循环（58k 次 `Arc` 克隆） | 1.037 ms | — |
| `job.append`（整篇 1MB） | 0.186 ms | — |
| `concat`（58k 行） | **1.378 ms** | — |
| 缓存回写（含旧整篇 `Galley` 析构） | 0.321 ms | — |
| **合计（墙钟 p50）** | **4.565 ms** | **0.241 ms（−94.7%，17.5×）** |

复现：

```text

```

##### 3.2.13.3 端到端（官方口径，同机 A/B，5 次复测）

| 档位 | 改前 p50 / p95 | 改后 p50 / p95 |
|---|---|---|
| 10 KB | 0.25 / 0.34 | **0.23 / 0.42**（噪声内，无变化） |
| 100 KB | 1.48 / 1.80 | **1.26 / 1.70** |
| **1 MB** | **17.62 / 18.93** | **14.35 / 16.5**（5 次：p50 14.29~14.58，p95 15.56~17.28） |

- 1MB **p50 −18.6%（−3.27 ms）**：与排版层省下的 3.84 ms 基本吻合
  （两套测量口径不同，差 0.5 ms 属合理）。
- 1MB **p95 仍在 16 ms 线上下**：5 次复测里 1 次低于 16 ms、4 次高 0.5~1.3 ms。
  按 `NFR-PERF-04`（p95 ≤ 16 ms）**尚不能宣称稳定达标**，只能说「贴线」。
- p95 的抖动不是本路径引入的：`p95 − p50 ≈ 2.1 ms`，与改动前的
  `18.93 − 17.62 = 1.31 ms` 同量级，来自每 ~150 ms 一次的
  `compute_stats` 结算（§3.2.10，1MB 单次 5.55 ms）与系统调度噪声。

##### 3.2.13.4 正确性（这是本节的验收重点）

快路径直接改写 `Galley` 的 `rows` / `num_vertices` / `rect` / `job.text`，
写错一格不会报错，只会表现为「光标偏一点」「少画一行」。故新增三条对拍用例
（`tests/presentation/highlight_layout_test.rs`），每条都拿**清空缓存后的全量
重建**当基准：

| 用例 | 覆盖 |
|---|---|
| `single_line_patch_matches_full_rebuild` | 等长替换 × 5（首行 / 正文 / 中间行 / 折行段 / 末行），带语法高亮；逐行字形、`ends_with_newline`、`galley.text()`、`num_vertices`、`num_indices`、`rect` 全比对 |
| `single_line_patch_handles_insert_and_delete` | 行内插入 / 删除 / 删除整行（应退回全量）/ 末行追加 |
| `patch_declines_when_wrapping_changes` | 逐字加长到跨过折行宽度：跨过那一步必须拒绝补丁，结果仍与全量一致 |

##### 3.2.13.5 已知边界

- 只处理**单行内**的编辑。插入 / 删除换行、跨行粘贴、整篇替换仍走全量重建
  （1MB 约 4.6 ms，可接受）。
- 折行数变化（在换行边界上打字）会让该帧退回全量——这正是
  `patch_declines_when_wrapping_changes` 钉住的行为。
- `Galley::intrinsic_size` 是 `pub(crate)`，补丁路径改不了，保持旧值。
  全仓只有 egui 的 atomics 读它，`TextEdit` 不读。
- `Arc::try_unwrap` 失败时（上一帧的 Galley 仍被别处持有）退化为一次整篇克隆
  （58k 个 `Arc` 克隆），仍比全量重建便宜，但比独占慢约 0.4 ms。

#### 3.2.14 侧栏「搜索」标签卡顿：范围过滤与读盘错序（2026-10-22）

**症状**：切到侧栏「搜索」标签（查询非空）后整窗冻结；输入框逐字卡顿。

**根因**（按代价排序，完整报告见 [`search-tab-performance-report.md`](./search-tab-performance-report.md)）：

1. **「当前文档」范围也读全盘**——`gather_candidates` 对 `only_document` 也传
   `include_disk = true`，先把整个工作区逐文件 `fs::read` + 解码，再 `retain`
   丢掉除目标外的一切。千文件工作区实测 **81–146 ms/次**（release，逐文件读盘
   等价成本，冷热缓存决定），且与活动文档大小无关；
2. **一帧跑两次**——开关行计数与结果列表各自调 `search_workspace`，成本 ×2；
3. 搜索内核每个字符比较分配 `Vec<char>`，且**每条命中重扫全文**求行号。

**修复**：范围过滤与读盘由同一个 `include_disk` 判断决定（`service.rs::search`）；
`gather_candidates` 新增 `only_document` 形参，单文档范围按 id 单取全文；
`toggle_row` 返回本帧唯一一次结果供计数与列表复用；`search_text` 改用零分配的
`char_eq_ignore_case` + 增量行号统计。

**实测（release，Windows x86_64）**

| 场景 | 修复前（等价成本） | 修复后 |
|---|---|---|
| 1001 文件工作区·「当前文档」单次搜索 | 81–146 ms | **0.00 ms** |
| 同上·切到搜索标签首帧 | ≈160–290 ms（×2） | **0.69 ms** |
| 1MB 文档·50 命中·一帧 | 11.5–11.7 ms（两次） | **6.0–6.4 ms**（p95 6.5） |
| 1MB 文档·切到搜索标签首帧 | ≈11.5 ms | **6.2 ms** |

复现：`cargo test --release --test presentation -- search_perf --nocapture`。
门禁：`tests/presentation/search_perf_test.rs`（单次 < 10 ms，两档均断言；切换首帧 < 100 ms，release 断言）。

### 3.3 防抖与窗口值校准（S8-06）

| 指标 | 目标 | 实测 | 结论 |
|---|---|---|---|
| 连续输入 20 字符（60 ms/字符，共 1.2 s）预览重解析次数 | **≤ 2** | 修复前 **7 次** → 修复后 **期间 1 次 / 累计 2 次** | ✅（见 OPT-012） |
| 10KB 文档解析 | ≤ 5 ms（`NFR-PERF-06`） | p50 **0.11 ms / p95 0.17 ms**（§3.0） | ✅ 余量 30 倍 |
| 1MB 文档解析 | 可编辑不卡顿 | p50 **17.7 ms**（一次性全量，§3.0） | ✅ |

**校准结论（两个窗口值均维持原值，理由如下）：**

- **预览防抖 150 ms —— 维持。** 它是「停手多久后重解析」：调大到 300 ms 会让预览在停手后再等
  300 ms 才更新，属可感知延迟；调小到 80 ms，则快速打字（80–120 ms/字）会频繁触发重解析，
  失去防抖意义。150 ms 处于「打字时不打扰、停手后立刻跟上」的区间。
- **撤销合并窗口 400 ms —— 维持。** 语义是「与**上一条记录**间隔 > 400 ms 才算新的撤销单元」，
  即**停顿**超过 400 ms 才断开，而非「每 400 ms 切一刀」。日常打字 200–300 ms/字会被合并成
  一整段，一次 Ctrl+Z 撤掉一整句——符合直觉。该语义已由
  `tests/domain/undo_test.rs` 固化（窗口内合并 / 窗口外断开 / 撤销后重置窗口）。

| 项 | 实测 | 说明 |
|---|---|---|

> **教训（对后续阶段同样适用）**：任何开启 LTO 的项目，若主二进制存在
> 「尚未接线」的空壳入口，`cargo bloat` 量到的体积**没有参考价值**——
> 它会把「还没用到的依赖」全部裁掉，从而给出「体积达标」的假象。
> 本项目用「临时探针 + 接线后切回」化解：**探针的存在期限应绑定在
> 「主二进制是否已引用该依赖」上，而不是永久保留**。
> 一个长期存在的体积探针会让人误以为主程序还没接线，是个会误导后来者的陷阱。
