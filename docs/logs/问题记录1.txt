2026-10-14 027
问题（用户请求）：
审查当前项目的依赖配置，找出未被实际使用或可被范围更小的替代方案取代的依赖，将其移除或精化引入范围，以减少包体积。

复查方法与工具（可复现）：
- 逐 crate 反查引用：`grep -rn "<crate>" src tests`。
- feature 来源反查：`cargo tree -e features -i <crate>`；重复版本扫描：`cargo tree -d`。
- 体积：同一 release 口径 `cargo build --release --bin rustmark` 前后对比（本机 target = x86_64-pc-windows-msvc）。

结论与变更（两处，均无功能代价）：
1. eframe 特性移除 "accesskit"：
   - 证据：全仓 `grep accesskit` 零命中；该特性只向屏幕阅读器暴露语义树，键盘导航 / IME / 焦点全走 egui 自身实现。
   - 效果：Windows 产物原链入的 accesskit / accesskit_winit / accesskit_windows / accesskit_consumer 四个 crate 全部移除，并连带去掉仅被它们引用的重复版本 hashbrown 0.15 / foldhash 0.1；跨平台 lock 合计移除 60 个包（含 Linux zbus / atspi / async-*、macOS accesskit_macos）。
   - 取舍：放弃屏幕阅读器可达性——对单人本地 Markdown 编辑器为可接受取舍。
2. ahash 由 "0.8" 收窄为 default-features=false + ["std","no-rng"]：
   - 证据：三处缓存 Map（application/markdown/service/{highlight,render,spell}_cache.rs）键**全是 DocumentId(u64)**，内部单调、非攻击者可控，无需 HashDoS 防护；ahash 的 runtime-rng 是依赖树中 getrandom 0.3.4 的**唯一**引入者。
   - 效果：getrandom 0.3.4 退出构建图（`cargo tree -i getrandom@0.3.4` → nothing to print）；种子改由 ASLR + 实例计数器派生（ahash 文档「最弱但可用」档），对缓存键无影响；与 eframe / egui 对 ahash 的用法一致。

复核后确认「保持现状」（记录以避免反复讨论）：pulldown-cmark 的 html（HTML 导出用 push_html）、toml 的 display（写盘用 to_string_pretty）、image 的 5 个位图格式（恰为 ALLOWED_MIME 白名单）、ureq 的 rustls（已是该库最小合规 TLS 组合）、rfd 默认特性与 eframe 的 x11/wayland（均 Linux 目标专属，对 Win / macOS 零影响）、default_fonts（UI 需要比例西文字形，项目未自带）。

体积实测：11,576,320 → 11,463,680 bytes（11.04 → 10.93 MiB，**−110 KiB，−0.97%**）。仍超 NFR-PERF-01 红线 0.93 MiB；本次只消掉「零功能代价」的浪费，剩余超限维持 metrics §2.4 的待决策。登记于 docs/dependencies.md §6、docs/metrics.md §2.5。

门禁：cargo fmt --check / check-arch / clippy --all-targets --all-features -- -D warnings / cargo test --all-targets 全绿（1623 用例，0 失败）。

2026-10-14 026
问题：
2、图片渲染失败，预览报错「图片无法加载 … 下载图片失败（https://…）：当前版本未内置 TLS，请改用本地图片或 http 地址」。现实文档里的远程图片地址绝大多数是 https。
根因（asset_loader.rs `load_remote`，S5-11 的历史取舍在真实场景翻车）：
- 首版为体积拒绝一切 HTTP 客户端 crate，手写 `TcpStream` + 裸 HTTP/1.0；TLS 需要外部实现，于是 https 被**硬编码拒绝**。判定「图片地址多为 http」的前提是错的——如今图床（CSDN、GitHub、对象存储）几乎全是 https。
修复（改用 ureq，http/https 同一条通路）：
- 引入 `ureq 3.4.2`（`default-features=false` + `["rustls"]`）：rustls 纯 Rust TLS、三平台行为一致、无系统依赖（native-tls 在 Linux 要 OpenSSL，交叉编译困难）；TLS/重定向/chunked 全部交出去。
- `load_remote` 只保留三条安全与资源边界：全局超时（沿用 `download_timeout`=5s）、边读边判体积硬上限（`max_inline_bytes`×2，防超大响应先全量进内存）、MIME 白名单（响应头优先、缺失按重定向后最终 URL 扩展名推断，判定次序与旧实现一致）。
- 非成功状态码显式报 `DownloadFailed`（带 HTTP 状态码）；`split_http_body` 手写切体原语随 TcpStream 方案退役（coding.rs 删除）。
- 体积代价：登记于 docs/dependencies.md §1 与 metrics.md §2.4；「明确不引入」清单里当年拒绝 reqwest 的理由仍成立，ureq 是体积最小的合规替代。
回归（asset_loader_test.rs）：
- 新增 `https_connect_failure_returns_download_error_not_panic`：https 到保留端口必须降级为 `DownloadFailed`（panic=abort 下坏图引用不得终止进程）。
- 新增 `real_https_download`（`#[ignore]` 需外网，手动跑）：用户报障的原始 CSDN 图床地址实测下载成功（mime=image/gif, 2056 bytes）。
- 原删除的 `https_url_is_rejected_explicitly_not_downgraded` 所守护的「不静默降级到明文 http」由 ureq 的 scheme 处理天然满足；本地 HTTP 服务下载用例（`remote_download_of_real_image_succeeds`）不改一行即通过。
门禁：cargo fmt --check / clippy --all-targets --all-features -D warnings / check-arch / cargo test --all-targets 全绿（asset_loader 26 条全过）。

问题：
1、左侧菜单切换到「检查」标签后，页面异常：侧栏右侧与编辑区之间出现一条竖向**纯黑**矩形（完整高度，从标签栏下一直贯穿到状态栏），编辑区整体被推右，侧栏内 lint 行的文字在该黑框左缘被截断。文件/大纲/搜索三个标签均正常。
根因（egui SidePanel 的布局保留规则 × lint 行的水平裸 label）：
- lint 行（`lint_row`）在 `Layout::left_to_right` 里用裸 `ui.label` 画说明文字——水平布局的 label **不换行**，文字超宽时 `min_rect` 直接溢出分配宽（面板内容区右界 232pt，插桩实测溢到 407.9pt）。
- egui `SidePanel` 给后续布局保留的空间不是 `exact_width` 的 240，而是**内容 response.rect 的最大 x**（egui panel.rs `allocate_left_panel(Rect::from_min_max(available_rect.min, rect.max))`）。于是侧栏实际占掉 [0, 415.9]，编辑区被推到 423.9。
- [240, 415.9] 之间**没有任何面板绘制**：侧栏底色被 `set_clip_rect` 裁在面板矩形内，溢出区谁都不画——真实渲染下露出交换链清屏色（黑），即用户看到的黑框。同一溢出对文件/大纲/搜索不触发，因为它们的行文本要么截断（files.rs 文件名「与大纲同一缺陷类」、outline.rs 标题），要么天然短；lint 说明是最长文案却漏了截断。
修复（与大纲/文件树同款 truncate 模式）：
- `lint_row`：说明文字改占「剩余宽 − 行号预留」（`OUTLINE_LINE_NO_W`，与大纲同款）并 `Label::truncate()`，超出显示省略号，绝不把行撑出面板；doc 注释完整记录根因链（供未来同类排版自查）。
- 同类隐患一并修（search.rs）：`group_header` 文件名与 `hit_row` 代码片段此前同样是水平裸 label——长文件名/长片段会以完全相同的机制撑出黑框；改为固定宽子区域 + truncate（高亮三段标签都在子区域内排）。
- 框架级防御（暂不做）：egui 该保留规则对任何视图的溢出都成立，理论可在 `sidebar_view::show` 统一钳制 response rect，但 egui 未提供干净的 API，且现有四个标签都已有截断约定；留待真出现第三个漏网再上框架级手段。

2026-10-14 023
问题：
按字体调研的推荐组合实施（承接 021）：① 内置西文等宽字体，让「设置页能选什么」不再取决于用户机器装了什么；② 内置 CJK 子集兜底，让精简 Linux / 最小化容器里中文不再整体变方框。
根因（021 遗留的两个环境依赖）：
- 发现机制只吃系统字体：多数 Windows 机器只有 Consolas / Cascadia、macOS 只有 Menlo——用户听说 JetBrains Mono 好用，下拉里根本没有，想选也无从选起；同一份配置换台机器观感就变。
- CJK 只吃系统字体：`candidate_paths` 找不到任何中文字体时（精简 Linux、最小化容器、部分 CI 镜像）界面中文**全部**为方框，且此前唯一的信号是一句 eprintln。
修复（assets/fonts/ + infrastructure/fonts.rs 装配）：
- 新增四份字体资产（合计 1.89MB）：JetBrainsMono-Regular.ttf（114KB）/ FiraCode-Regular.ttf（141KB）/ IBMPlexMono-Regular.ttf（63KB）为可选等宽字体；NotoSansSC-Subset.ttf（1.57MB、7854 字形）为 CJK 兜底。均只含 Regular 字重（egui 不合成加粗，加粗文本回落 Regular，与系统 CJK 兜底同取舍；全字重会把体积推到 2MB 以上）。
- CJK 子集化方法（可复现）：`pyftsubset NotoSansSC-Regular.ttf --text-file=gb2312.txt --no-hinting --layout-features='' --name-IDs=0,1,2,3,4,5,6`；`gb2312.txt` 由 GB2312 双字节码位经 Python `gb2312` 编解码器枚举而成（94×94 网格可解出的 8105 字符 = 6763 汉字 + 1342 符号），未改任何字形。GB2312 之外的生僻字（堃玥囧等）在有系统中文字体的机器上仍由系统字体渲染。
- 数据模型：`FontSource` 增加 `FontBytes::{Path, Static}`——内置资产没有路径（`include_bytes!` 进二进制），旧「只做存在性检查」约定只对磁盘候选成立；`discover_font_sources` 改为内置打头 + 按**显示名**去重（用户装了同名字体时内置赢，避免下拉出现两个「JetBrains Mono」）。
- 兜底链扩展为「西文 → 数学 → 系统 CJK → 内置 CJK」：新增 `builtin-cjk` 键，**无条件**挂载且排最末——系统字体观感更好、字重齐全，内置子集只是「一台机器上什么中文字体都没有」时的保险；顺序反了会让有雅黑的用户也被迫用子集（生僻字反而变方框）。
- `install_editor_fonts` 的缺字体警告改为如实表述：有内置兜底，不再是「中文将显示为方框」，而是「已改用内置 Noto Sans SC 子集（GB2312），生僻字在此环境下仍可能为方框」。
回归（fonts.rs 新增 3 条，17 条全过）：
- `builtin_editor_fonts_are_registered_and_selectable`：三款内置字体已登记 font_data、出现在下拉、且排在哨兵之后最前（钉住「跨平台一定有得选」）。
- `builtin_cjk_sits_after_system_cjk_in_both_families`：内置子集排在系统 CJK 之后、族最末（钉住链序，防「优化」反了）。
- `builtin_cjk_subset_alone_provides_glyphs_for_chinese`：**决定性验证**——只用默认定义 + 内置子集装配（刻意不挂系统 CJK），`set_fonts` 后比例族与等宽族对「中文编辑器文档预览测试，。、「」」都有字形；同时守护随仓库分发的字体文件本身是好的（畸形字体在 panic=abort 下直接终止进程）。
资产来源与许可（assets/fonts/Fonts-LICENSE.txt 逐款列明）：
- 三款西文字体与 Noto Sans SC 均为 SIL OFL-1.1（可随软件捆绑再分发，禁单独售卖，衍生须改名）；版权串取自各字体 name table（如 "Copyright 2020 The JetBrains Mono Project Authors"）；OFL-1.1 全文自官方站 openfontlicense.org 抓取（scripts.sil.org 已 403 迁站）。
- 下载渠道备注：GitHub raw / jsdelivr 在本沙箱不可达，字体经 npm 镜像的 @expo-google-fonts TTF 分发包获取（文件与上游一致）；pip 镜像实际可用（022 记录的「pip 被沙箱拦截」是瞬时失败，本次已装上 fonttools 4.66.1）。
- 未纳入：Sarasa Mono SC（更纱黑体，中英 2:1 等宽，编辑区对齐最佳）与 STIX Two Math（符号覆盖最全）在 npm 无分发包、GitHub 不可达，需手动下载后放入 assets/fonts/ 并补 Fonts-LICENSE.txt。

2026-10-13 022
问题：
2、（016 复报）KaTeX 数学公式中存在的数学符号不齐缺失：预览里的数学符号出现方框（豆腐块），渲染不全面。
