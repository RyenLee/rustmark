问题（050 优化候选③：`diff_replace` 是唯一的「确定性缺陷」）：
两轮归因（049 / 050）把 1MB 击键帧拆开后，`editor_ops::diff_replace`（`transform.rs`）是
唯一一处**纯浪费**：它挂在「每击键一次」的路径上（`editor_view::show` 的 `changed()` 分支），
却先把两整篇文本 `chars().collect::<Vec<char>>()`（1MB = 2 × 35 万 char，约 2.8MB 分配 +
两遍 UTF-8 解码），再用两次 `char_to_byte`（内部 `char_indices().nth(k)`，O(k)）把字符索引
换回字节——**做这一切只为求一个公共前后缀**。与 046「为两个整数付 O(全文)」同性质，
release 实测 6.93ms（049 E8）。

处置（字节层前后缀 + 字符边界回退/收拢；对外语义不变）：
- 前后缀改在**字节层**比较（`as_bytes()` 逐字节）：**不分配、不解码**。
- 字节前缀可能落在字符中间（`é` ↔ `è` 共享首字节 `0xC3`，公共前缀停在 2 字节字符的第二
  字节上），故用 `str::is_char_boundary` **回退**前缀、**收拢**后缀到字符边界。
  可这么做的前提：UTF-8 是自同步编码——某位置是否为字符边界只取决于**该位置自身**是否为
  续字节（加上文末），而公共前缀段两侧逐字节相同，故边界判定两侧一致。
- 字符索引此时只需在**前缀处**算一次（`byte_to_char(old, byte_start)`，两侧同值），
  光标 =「前缀字符数 + 插入内容字符数」；`anchor_char` = 纯删除时取该前缀字符数。
- 三处只有新实现才会踩的路径各配一条单测；另加一条**等价性基准**：把旧的字符层实现
  原样保留为 `reference()`，对 16 组输入逐字段比对（含中文 / 4 字节字符 / 上面两个边界）。

实测（release，p50，1MB 中文 Markdown）：

| 量 | 改前 | 改后（三轮独立运行） |
|---|---|---|
| `diff_replace` 文末追加（前缀最长 = **最坏**位置） | 6.93 | **0.24 / 0.25 / 0.24** |
| `diff_replace` 文档中点替换 | ~6.9（旧实现与位置无关） | **0.33** |
| 1MB 击键帧 p50（E1） | 40.43 / 40.62 / 40.92 | **34.55 / 33.73 / 35.48** |
| 1MB 击键帧 p95 | 43.42 | **37.41 / 36.12 / 38.56** |
| 1MB 同运行空闲帧 | 7.06 | 7.32 ~ 7.65 |

改后三轮 E1 区间（33.7~35.5）与改前（40.4~40.9）**无重叠**，差额 5.4~6.4ms 。

结论：
1. **单次调用 ×27**，击键帧同步降 6.4~7.2ms——降幅与该单项的绝对降幅一致，
   反证这笔钱确实全部出自 `diff_replace`（不是巧合的噪声）。
2. **位置敏感度消失**：旧实现无论改哪里都要整篇字符化（恒 6.9ms）；新实现只在**前缀处**
   做一次字符计数，文末 0.24 / 中点 0.33——量级恒定。（注意：文末追加恰恰是前缀**最长**
   的最坏位置，不是有利位置。）
3. **对外语义零变化**：`TextEdit` 各字段逐字段等同旧实现。
4. **剩余缺口未变**：1MB 仍超 16ms 2.3×，大头是状态栏整篇统计（9.30ms）+ 排版层
   （9.09ms）+ 空闲帧（7.5ms）——即 050 的①②待办，均在应用层，**自绘仍无收益**。

变异验证：去掉两处 `is_char_boundary` 调整 → 三条新单测立即全部 panic 在「非字符边界切片」上

问题（用户诉求，继承 044 勘察的「编辑区框不满面板」议题；用户选定方向 A「框撑满面板」）：
编辑区那个圆角框只包住文本，短文档下框底到状态栏之间是一大片裸底色。
本机实测（1280×800 窗口、关预览与侧栏）：框高 96pt，编辑区视口高 625pt。

根因（044 已逐条像素取证，本条只记结论）：
- 那个框是 `TextEdit` **自带**的 frame，尺寸 = 控件尺寸；
- 控件高度由 `desired_rows(行数)` 与排版结果决定，与「编辑面板有多高」无关；
- 外层 `ScrollArea` 的 `auto_shrink` 默认是 `Vec2b::TRUE`，语义是「内容多高、滚动区就多高」
  （egui 0.37 `scroll_area.rs` 实证），于是短文档下滚动区自身也收缩到文本高度——
  既让框不满面板，也让横滚动条贴在「收缩后的框底」而不是面板底。

修复（`src/presentation/views/editor_view.rs`，方向 A「框撑满」）：
- 滚动区加 `.auto_shrink([false, false])`——`inner_rect` 从此保持满高，
  `ui.clip_rect()` 才等于真实视口高，横滚动条也随 `inner_rect` 落回面板底；
- `TextEdit` 加 `.min_size(vec2(0.0, viewport_h))`，`viewport_h` 取闭包内的
  `ui.clip_rect().height()`（已扣滚动条占位）。两个易错点都写进了代码注释：
  ① 不能用 `ui.available_height()`——`content_max_rect` 的顶端是 `inner_rect.min − offset`，
     滚动后它反而随 offset 变大，会把 frame 越撑越长；
  ② 宽度一个点都不能给——egui 算宽度是
     `allocate_width = desired_width.at_most(available_width).at_least(min_size.x)`，
     `min_size.x` 会**顶掉** `available_width`，把正文撑出视口、凭空生出横滚动条。
- ⚠ 撑满剩余高的滚动区会把**其后**在同层 Ui 绘制的元素推出面板底缘（既有硬规则）。
  已核实编辑区面板内滚动区之后只有 `ctx` 绘制的浮层菜单（`draw_spell_menu`），
  不参与同层布局，故本次改动安全；注释里写明「后续要在编辑区底部加常驻提示必须放在滚动区之前」。
