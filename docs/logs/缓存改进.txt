egui 0.33 的 `TextEdit` 在处理大文本时出现卡顿，核心原因在于**即时模式 GUI 的每帧重绘特性**与**文本布局的高昂开销**相叠加。egui 在每次编辑时，默认会重新布局整个文本，对于数千行的文本，这会直接导致帧率骤降。以下是针对性的优化思路与方案。

### 🎯 核心卡顿原因

卡顿主要源于三个层面，理解它们有助于选择正确的优化路径：

1. **文本布局开销**：`TextEdit` 每次内容变化，都需要通过 `LayoutJob` 重新计算所有字形（glyph）的位置、换行和尺寸。这是最昂贵的操作，其耗时与文本总长度呈线性关系。
2. **缓存机制局限**：egui 本身有 Galley 缓存，其键值基于整个 `LayoutJob` 的哈希。对于长文本，**每次编辑都会导致整个哈希变化**，缓存几乎完全失效，无法避免全量重算。
3. **渲染后端与字体光栅化**：在 0.33 到 0.34 的过渡期，有用户报告在 **wgpu 后端**下出现文本性能退化，性能分析显示大量时间消耗在 `allocate_glyph_uncached`（未缓存的光栅化字形分配）上。此外，若字体大小在每一帧都发生变化（如随缩放动态计算），字形将永远无法被缓存，导致持续的重光栅化开销。

### 🛠️ 分场景优化方案

根据你的使用场景，可以从以下方案中选择或组合使用。

#### 方案一：视口虚拟化（适用于纯展示/只读大文本）

如果你的 `TextEdit` 主要用来**展示**大段文本，而非频繁编辑，这是最有效的方案。

- **思路**：只对当前滚动视口内可见的文本进行布局和渲染，而非整个文档。
- **实现**：将 `TextEdit` 放入 `ScrollArea` 的 `show_viewport` 回调中。在回调内，**根据传入的 `rect` 参数，仅提取并展示对应区域的文本子串**给 `TextEdit`。
- **注意**：不要直接在回调中 `ui.set_clip_rect(rect)` 后展示完整文本，这仍会创建全尺寸的 Galley，无法节省布局开销。需要配合文本切片逻辑。
- **社区参考**：egui 官方示例中的 **“large scrolling fields”** 演示了相关的虚拟化思路，可以作为实现起点。

#### 方案二：段落级缓存（适用于可编辑长文本，需修改/等待 PR）

这是从根源上优化编辑性能的方向，但可能需要等待官方合并或使用自定义分支。

- **思路**：将长文本按换行符 `\n` 切分为独立段落，为每个段落单独缓存其布局结果（Galley）。编辑时，**只有被修改的那个段落需要重新布局**，其余段落直接复用缓存。
- **性能预期**：在官方 PR #5411 的基准测试中，编辑一个 **2000 行的字符串**，单次编辑的布局耗时从 **~8ms 降至 ~300µs**（微秒），提升约 **25 倍**。
- **当前状态**：该优化已包含在 PR #5411 中并被合并，但**尚未进入 0.33.x 稳定版**。你可以：
    - **关注后续版本**：检查 egui 0.34 或更高版本是否已集成该优化。
    - **使用 Git 分支**：在 `Cargo.toml` 中临时指向包含该 PR 的 Git 提交，以立即获得性能提升。

#### 方案三：渲染后端与字体优化（通用调优）

这些设置可以缓解由字形光栅化缓存失效引起的卡顿。

- **切换渲染后端**：如果当前使用 `egui-wgpu`，可以尝试切换回 `egui-glow`。有用户报告从 0.33.3（glow）升级到 0.34.1（wgpu）后出现性能下降，而 glow 后端则保持流畅。
- **关闭字体微调与亚像素混叠**：在 `egui::Context` 的 `FontDefinitions` 或 `TextStyle` 设置中，尝试禁用 `font_hinting` 和 `subpixel_binning`。这能提高字形缓存的命中率，但会轻微牺牲文本渲染清晰度。
- **固定字体大小**：**避免在每一帧动态计算字体大小**（例如根据相机变换或缩放级别）。如前所述，变化的字体大小是字形缓存的“病态案例”，会导致持续的未缓存光栅化开销。应尽量使用固定的、预定义的字体尺寸集合。

### 🔍 诊断与验证

在实施优化前后，建议进行量化验证：

- **使用性能分析工具**：使用 **`puffin`** 或 **`samply`** 对应用进行性能剖析。重点关注 `egui::text::layout`、`allocate_glyph_uncached` 等函数的耗时占比，以精确定位瓶颈。
- **构建基准测试**：参考 PR #5411 中的测试程序，生成一个包含 2000-50000 行的字符串，在 `TextEdit` 中编辑并测量每帧耗时，以客观评估优化效果。
- **启用 Release 构建**：确保你是在 `--release` 模式下测试。Debug 模式下 Rust 的文本处理性能会下降数十倍，这本身就会造成严重卡顿。

### 💎 总结

**首选方案**是判断你的场景：若为**只读大文本**，立即采用**视口虚拟化**；若为**可编辑长文本**，优先确认能否**升级到包含 PR #5411 的版本**。同时，检查并优化**渲染后端与字体设置**，避免动态字体大小。通过 `puffin` 等工具量化瓶颈，能确保优化方向正确。
