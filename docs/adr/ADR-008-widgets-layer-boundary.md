# ADR-008 · `widgets` 层的边界：只收「写错不报错」的不变式

- **状态**：已接受（2026-10-19）
- **决策者**：项目架构负责人
- **关联任务**：T8（优化任务清单 C2）
- **关联文档**：`src/presentation/widgets.rs` 模块文档、`docs/stages/06-表现层与交互实现.md`、
  `docs/logs/问题记录1.txt`（问题 061 / 065）、`ADR-007`

## 背景

T8 的原始诉求是「把 egui 布局硬规则固化为 `widgets/` 层可复用组件」，预期收益是
「下一次 egui 大版本升级受影响面从几十处散点收敛到几个封装点」。

动手前先核对了三个事实：

1. **`src/presentation/widgets.rs` 是空壳**：阶段 06 建的文件，只有一行模块文档，
   零个组件、零处引用；
2. **egui 使用面很大**：72 个文件、767 处 `egui::` 引用，频次最高的是
   `vec2`(67) / `pos2`(60) / `Id::unique`(36) / `Sense::hover`(31) / `Stroke::new`(22) /
   `CornerRadius::same`(22) / `Rect`(20) / `FontId`(34)；
3. **升级真正改的是构造器**：0.33→0.37 改签名的是 `Rounding`→`CornerRadius`、
   `Margin` 由 `f32` 改 `i8`、`Frame::none()`→`Frame::new()`——全部是机械替换
   （编译器逐个报错，改起来是体力活而非判断活）。

也就是说，T8 的预期收益**对构造器不成立**：薄薄包一层 `widgets::v2(x, y)` 只是多一次
跳转，升级时反而要同时改封装与调用点两处。真正的成本在**语义变化**上
（`Ui::horizontal` 的初始高、`scope_builder().response` 的返回、面板按内容 rect 保留宽度），
那些没有一处是「封装一次就免疫」的。

## 决策

### 1. 只收满足三条的组件

| 条件 | 理由 |
|---|---|
| 同一配方在 ≥2 处出现 | 只出现一次不叫模式 |
| **写错不报错** | 错误只表现为视觉错位/交互失效，编译期、类型系统、常规单测都拦不住 |
| 正确写法与直觉写法不同 | 直觉写法看起来完全合理，这正是它反复被写错的原因 |

### 2. 本期落地 3 个组件，覆盖 8 处调用点

| 组件 | 封住的不变式 | 调用点 |
|---|---|---|
| `widgets::row::clickable_row` | 多段 hover-sense 内容会吞掉整行点击（问题 1）；`with_layout` 不限子 Ui 高导致整行浮中部（问题 065）；`horizontal` / `horizontal_top` 的取舍 | 文件树 / 大纲 / 搜索命中 / 检查结果 4 处 |
| `widgets::text::elided_segment` | 限宽段的**高度必须取自已排控件**，传 0 会让文字下沉半个行高（问题 065）；截断必须发生在**一段**文本上（问题 033） | 大纲 / 检查 2 处 |
| `widgets::text::put_elided` | 定位矩形里的文本必须**贴左**（问题 061） | 面包屑 / 标签标题 / 最近打开 / 快速打开 4 处 |

`elided_segment` 的 `measured` 参数类型定成 `Rect` 而不是 `f32`，是刻意的：让「传 0」
在类型层面说不出口——只能从已排控件那里取真实矩形。

### 3. 明确**不收**的东西

| 不收 | 理由 |
|---|---|
| `vec2` / `pos2` / `Rect::*` / `Sense` / `Color32` / `FontId` / `Stroke` | egui 的稳定词汇；封装是负收益（见背景第 3 点） |
| `horizontal_top` / `Separator::spacing(1.0)` / 按 `clip_rect` 推坐标 / `add_space` 双计 / `max_rect` 污染后的块级限宽 | 它们是**调用点的选择**而非可复用代码。封成别名会隐藏 egui API 本身，而相关注释引用的正是 egui 的名字（`Placer::expand_to_include_rect`、`UiBuilder::sense`）——隐藏后注释与代码对不上 |
| 按钮 / 标签 / 开关等普通控件 | 二次封装普通控件是「自建 GUI 框架」的起点，调用点失去 egui 文档与示例的直接对应关系 |

## 顺带查出的真回归：061 的 `halign(LEFT)` 在 0.37 下是空操作

`put_elided` 的第一版照抄 061 记录的写法
`ui.put(rect, Label::new(t).truncate().halign(Align::LEFT))`。真帧实测（240pt 矩形）：

| 写法 | 字形左缘 |
|---|---|
| `put` + `truncate` + `halign(LEFT)` | 121.84（居中） |
| `put` + `truncate` | 123.00（居中） |
| `scope_builder` + `left_to_right` | **10.00（贴左）** |

原因：`Ui::put` 的子 Ui 布局是 `centered_and_justified(TopDown)`，Label 先
`allocate_exact_size(galley.size())` 拿到一个**已被父布局居中**的矩形；`halign(LEFT)`
只决定字形相对**这个矩形**的落点（`rect.left_top()`），对矩形自己被摆在哪毫无影响。

这意味着 061 记录的三处修复（标签标题、面包屑、最近打开）自 egui 0.37 升级起
**实际已失效**：短标题一直按自身宽度居中。为何一个版本无人发现——既有的
`tabs_never_overlap_and_titles_stay_in_their_tab` 只断言「标题右缘不越标签右缘」，
而居中偏移 `(name_avail − 文字宽)/2 ≈ 60pt` 远小于右缘余量 ~90pt，短标题**即使居中
也不越界**。判据没有区分力。

修法与新增判据：

- 实现改为 `scope_builder` + `left_to_right`，与字体、文本长度、是否 elide 无关；
- 在既有用例里补「各标签标题左缘偏移恒定」判据（用**不同长度**标题互比，
  不依赖 `TAB_PAD` 取值）。变异验证：退回 `put + halign` 后实测偏移为
  `[43.0, 38.8, 11.0, 50.5]`、极差 39.5pt，用例当场变红。

## 备选方案与代价

| 方案 | 收益 | 代价 | 结论 |
|---|---|---|---|
| 全面封装 egui（所有构造器走 `widgets`） | 表面统一 | 767 处调用点全部改写；升级时两处都要改；调用点与 egui 文档脱节 | 否决：净负收益 |
| 只写文档/wiki，不封装 | 零改动 | 「写错不报错」的一类靠自觉，历史上已复发 4 次 | 否决 |
| 拆出独立 crate 承载 widgets | 编译隔离 | 与 ADR-007 同因否决（单消费方、crate 编译单元语义） | 否决 |
| 本期方案：3 个不变式组件 + 明确的不收清单 | 每个组件都对应已归档缺陷与可执行判据 | 覆盖面窄 | **采纳** |

## 后果

- **正面**：4 类已复发缺陷（行点击、段错位、多段截断溢出、定位文本居中）从「靠注释与
  记忆」变成「靠类型与封装形状」；061 的失效被查出并修复，且有了有区分力的判据。
- **负面（诚实交代）**：`widgets` 的覆盖面**不等于**「egui 升级面收敛」。构造器类改动
  （`CornerRadius` / `Margin` / `Frame`）仍需逐个调用点机械修改；语义类变化（面板保留
  宽度、首帧测量 pass、`scope_builder().response`）只能靠真帧探针测试兜住，
  封装无法免疫。
- **触发下一次扩充的条件**：某条布局纪律第 3 次复发，或某段配方在 3 处以上重复。
  判定仍按本文的三条标准，不要因为「看起来能抽」就抽。
