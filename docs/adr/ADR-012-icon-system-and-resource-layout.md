# ADR-012 · 图标系统与资源布局

- **状态**：已接受（2026-10-21 补记；各项决策均已落地）
- **决策者**：项目架构负责人
- **关联任务**：V11-54a R-10（渲染管线）/ T2（字体随包分发）/ 问题 069（草稿旁车）
- **关联文档**：`src/presentation/icons.rs`、`src/domain/document/repository.rs`、
  `src/infrastructure/persistence/fs_document_repository.rs`、
  `src/infrastructure/fonts/`（R-20 拆分后）、`scripts/package-{linux,macos,windows}`

## 背景

编辑器的「非代码资源」散落在三处，各自曾因「用了最省事的做法」踩坑：
图标用字体字形（豆腐块）、草稿只存内容丢了文件名、字体想 `include_bytes!`
内嵌。三者决策同源——**资源要么可被静态保证，要么约定一个不会悄悄失效的
磁盘布局**，不能用「能跑就行」覆盖。

## 决策

### 1. 图标一律向量手绘，废止字形图标

原实现（`UiAction::icon`）用**字体字形**当图标（`B` / `I` / `<>` / `🔗`…），
两个方向都不及格（`icons.rs` 头部注释记载）：

1. **依赖字体覆盖**：字形一旦落在已装载字体之外，界面上就是一个豆腐块
   方框——比没有图标更糟。实测 `▾ ◂ ▦ ⌫ ⇥ ⤒ ↹ ✓` 等一批符号无字形，且
   覆盖率随平台变化，只能逐台实测，无法静态保证。
2. **表达力贫乏**：单字形只能是「一个字符」，谈不上配色、层次与风格。

现在图标全部改为 [`Painter`] 向量绘制：几何在代码里，渲染只依赖 egui 本身，
跨平台一致，且**每一个像素都可被测试断言**（图元数量、外包矩形、居中度）。

### 2. 图标规格 = 数据，不是代码分支

每个图标是一张 [`IconOp`] 表（`icons.rs::spec` 取值）。表里每个图元自带两维
自由度：

- **绘制方式** [`Paint`]：描边（线稿）或实心（色块）——线稿与实心可以出现在
  同一套 UI 里而风格不散；
- **配色角色** [`Tone`]：主色（随控件文字色，悬停/按下自动换档）或强调色
  （主题强调色，点出图标里「最该被看到」的那一笔）。

于是「多样式组合」不是口头承诺：新图标 = 往表里追加几行图元，描边/实心、
主色/强调色自由搭配，无需改渲染器一行代码。渲染器（`paint_icon`）只做一件事：
把 **16×16 设计栅格**（`GRID`）等距缩放进目标矩形，改图标尺寸只改调用方的矩形。

栅格纪律由单元测试把守：`icon_ops_stay_inside_the_grid` 断言任何图元不得越界。
现有规格以**描边**为主是刻意的——16pt 量级上实心色块会糊成一片，线稿的
呼吸感更接近专业编辑器的工具栏；`Paint::Fill` / `IconOp::Circle` 等实心图元为
更大尺寸场景（欢迎页主操作、关于页）预留。

### 3. 草稿旁车协议：内容文件 + 路径旁车（问题 069）

未保存草稿写到 `drafts_dir/<doc_id>.draft`（异常退出后可恢复，需求 §4.3）。
`path` 为 `Some` 时**同时**写旁车文件 `<doc_id>.draft.path`
（`fs_document_repository.rs:342`），记录文档的原始路径。

**为什么需要旁车**：草稿以 `doc_id` 标识，不以路径标识。只存内容的草稿恢复后
一律是「未命名」，标签条丢失原始文件名（`问题 069`）；多份草稿之间更是完全
无法区分。旁车只记一行路径字符串，把身份还给了草稿。

**布局纪律**：
- 旁车写在内容**之后**——内容才是恢复的命根子，路径丢了最多退回「未命名」，
  内容丢了才是事故（`fs_document_repository.rs:339` 注释）；
- 旁车损坏（截断 / 非法路径）**不当致命**，退回 `None`：调用方 `pending_
  recoveries` 一失败就会丢掉**全部**待恢复草稿，为一行路径赔上所有内容不值当
  （`load_draft_path` 的 `FilePath::new(...).ok()` 吞掉非法）；
- `clear_draft` 一并删除旁车：留着就是磁盘垃圾，且文档 ID 复用时旧路径会被错
  当成新文档身份（`fs_document_repository.rs:386` 注释）。

### 4. 字体外置，随包分发而非内嵌

字体资产放在 `assets/fonts/`，**运行时由 `discovery.rs` 邻近 `current_exe()`
发现**（`fonts/mod.rs:148`），而不是用 `include_bytes!` 编译进二进制。三个来源
共用**同一条发现路径**：内置（`assets/fonts/`）→ 项目 `fonts/` → 系统等宽候选
（`system_mono_candidates` 三平台分支），`discover_font_sources` 接受注入根目录
（R-20 拆分后），项目字体优先于系统候选。

**为什么外置**：
- 保持 release 二进制精简（R-26 后约 11 MiB；内嵌多套字体 + CJK 子集会显著
  膨胀，且每次换字体都要重新编译）；
- 用户可在 `assets/fonts/` 下覆盖 / 追加项目字体，无需改代码或重编译；
- 真实资产缺失（干净克隆）时测试**自动 skip**（`builtin_font_assets_present()`
  守卫，R-20 引入），不污染 CI。

**发行包形态约束**：`scripts/package-{linux,macos,windows}` 三个脚本都按
`assets/fonts/` 布局分发——这条约定是 R-20 拆分时的硬约束，拆分**不得**改动
该目录布局（T2 刚落地）。

## 后果

**收益**：

- 图标跨平台零豆腐块，且渲染结果可被像素级断言（线稿/实心、主色/强调色各有
  单测）；
- 新图标只加数据不加渲染代码，风格不会散；
- 草稿恢复保留文件名，多份草稿可区分；
- 字体二进制精简、可覆盖、可在无资产机器上干净测试。

**代价**：

- 向量图标比字形图标写起来啰嗦（每个图元要手绘几何），但换来一致性与可测性；
- 字体发现依赖运行时文件系统布局，打包脚本必须保证 `assets/fonts/` 随包
  分发（已在三个 `scripts/package-*` 中约束）。

**已知不覆盖**：

- 图标的**取用约定**（哪个动作配哪个图标）在 `presentation` 层，不在本 ADR；
- 字体**装配顺序**的约束（选中字体置顶、CJK 追加到末尾）由 R-20 的
  `assembly.rs` 纯函数保证，本 ADR 只管「资产从哪来、以什么形态分发」。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 图标继续用字体字形 | 覆盖率随平台变化无法静态保证，豆腐块比没有更糟；单字符无配色/层次 |
| 图标用图片资源（PNG/SVG 文件） | 引入资源加载与缩放模糊；不如向量在代码里可被像素断言 |
| 字体 `include_bytes!` 内嵌 | 膨胀二进制、换字体要重编译、无法让用户覆盖；与「三来源共用一条发现路径」冲突 |
| 草稿只存内容不记路径 | 恢复后一律「未命名」，多份草稿不可区分（问题 069 的实踩缺陷） |
