# ADR-011 · 动作路由与双意图

- **状态**：已接受（2026-10-21 补记；决策早于本 ADR，已在代码中落地）
- **决策者**：项目架构负责人
- **关联任务**：V11-54a R-04（动作接线）/ 问题 066（跳转意图）/ 动作路由史（T6）
- **关联文档**：`docs/spec/architecture-constraints.md`、`src/app/frame/actions.rs`、
  `src/presentation/views/scroll_sync.rs`、`ADR-008`

## 背景

编辑器有两类「看起来能跑、实际静默失效」的缺陷，根源都是**同一个动作有
多个去向、却没有一个地方把它们穷尽登记**：

1. **动作分发**：原 `EditorApp::execute` 是 46 分支的 `match` + `_ => {}`
   兜底。兜底的代价不是「多写一行」，而是**新增 `UiAction` 变体时编译器
   不会提醒你接线**。历史上 `Ctrl+S` / `Ctrl+N` / `Ctrl+Shift+S` / `Ctrl+H`
   / `Ctrl+Shift+F` 都这样静默失效过——动作表里有、菜单里有、快捷键也
   注册了，按下去毫无反应，零报错。

2. **跳转意图**：「把某个偏移滚进视口」这件事，查找「下一个」（连按 F3，
   连续触发）与大纲 / 搜索跳转（离散点击）对「跳过去之后要做什么」的理解
   **不一样**。硬套同一策略必坏一头：连续触发每次把命中顶到视口上部会
   剧烈跳动；离散跳转若套用「已可见就不动」会让点击看起来毫无反应。

两件事分别落在 `app` 层（`actions.rs`）与 `presentation` 层（`scroll_sync.rs`），
但决策同源：**把「多意图」变成「穷举 + 显式变体」，让编译器与测试替你盯
住每一个分支**。

## 决策

### 1. 动作路由：穷举表 + 薄分发器，且**故意不写 `_ =>` 兜底**

`UiAction` → 去向由 `action_route(action) -> ActionRoute`（`actions.rs:208`）
**穷尽声明**。`ActionRoute`（`actions.rs:176`）只有五个变体：

| 变体 | 含义 |
|---|---|
| `Overlay` | 浮层类；具体打开哪个浮层由 `Overlay::opened_by` / `also_opened_by` 唯一确定，**本表不重复登记**（两处事实必然漂移） |
| `Format` | 格式类；统一交 `apply_format`，它自己按 action 分派 `FormatKind` |
| `GotoTab(usize)` | 标签跳转（`Ctrl+1..9`） |
| `Handler(fn(&mut EditorApp))` | 单一处理器（统一签名的 trampoline） |
| `Unbound` | 动作表里有、但**尚未接线**（机制预留，当前实例为零） |

`execute`（`actions.rs:77`）只剩分发，三个入口（菜单 / 快捷键 / 命令面板）
**全部汇聚到这里**，因此不可能出现「菜单里有的操作，快捷键触发的结果不一样」。

**这张表故意不写 `_ =>` 兜底**——它的唯一价值就是「新增 `UiAction` 变体时
编译失败，逼你选一个去向」。一旦写兜底，漏接线的动作会重新退化成静默失效，
那正是本表要根除的缺陷类型。

`Unbound` 保留而不是删除（`actions.rs:197` 带 `#[allow(dead_code)]`，是
「机制预留、实例为零」的显式声明）：R-04 把 `Revert` / `InsertImage` 接线后
本变体当前无实例，但「本期确有接不了的线」需要一个显式出口——写在路由表
里 + 在测试清单里登记，提交 diff 即可见；删掉变体只会把这条路变成「路由到
一个空 trampoline」，那正是静默失效本身。

配套守卫 `unbound_actions_are_explicit`（`actions.rs:439`）：断言当前 `Unbound`
清单与代码一致，「新增 Unbound 必须同步更新本断言」。这条断言的作用不是禁止
新增 `Unbound`，而是让每一次新增都必须在**提交时显式说明**。

### 2. 跳转意图：双意图枚举，而非运行时猜

`RevealIntent`（`scroll_sync.rs:58`）穷举两种意图：

- `Top`：一律滚到该行顶部（贴视口顶，留 `TARGET_MARGIN`）——离散跳转用；
- `IntoViewport`：已在视口内则不动，否则落到视口上部 1/4 处——查找「下一个」
  连按防抖用。

落点与「预览区点击 → 编辑区」的 `drive_editor` 对齐（同为 `行顶 − TARGET_MARGIN`）：
两条跳转路径的手感必须一致，否则用户会发现「点预览跳得准、点大纲对不齐」。

**不能用「一个布尔 + if」表达**：布尔的两个取值没有名字，调用方永远记不住
哪个是「防抖」哪个是「顶到头」，且未来再加第三种意图（如「居中」）会逼着
所有调用点改签名。枚举让「意图」成为一等类型。

## 后果

**收益**：

- 新增 `UiAction` 变体而不接线 → **编译失败**，把「静默失效」提前到编译期。
- 动作去向集中在 `action_route` 一处，浮层 / 格式 / 标签 / 处理器四类不会
  各写各的分发副本（历史上 `Overlay` 的反向映射曾与正向表漂移，导致
  `Ctrl+H` 替换丢失）。
- 跳转意图显式化后，连续 F3 与离散大纲跳转不再互相将就，手感各自正确。

**代价**：

- `action_route` 是一张需要随 `UiAction` 同步维护的表（用 `unbound_actions_
  are_explicit` 把「漏更新」也变成编译/测试失败）。
- `RevealIntent` 增加了一个枚举类型，调用点必须显式选意图（轻微啰嗦，但
  正是这种啰嗦挡住了「随手猜意图」）。

**已知不覆盖**：

- `UiAction` 的**注册**（菜单项 / 快捷键绑定）仍由 `presentation::shortcuts`
  负责，不在本 ADR 范围；本 ADR 只管「动作一旦产生，如何可靠地执行」。

## 备选方案

| 方案 | 否决理由 |
|---|---|
| 保留 `_ => {}` 兜底 | 正是历史上五处静默失效的根因；漏接线无任何信号 |
| 用宏自动生成路由表 | 可读性差，且「显式 `Unbound` 出口 + 守卫断言」本就是为了在 diff 里**可见**，自动生成反而稀释了这个信号 |
| 跳转意图用布尔参数 | 两个取值无名字、易记混；加第三种意图要改所有调用点签名 |
